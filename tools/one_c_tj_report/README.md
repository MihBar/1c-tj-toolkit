# PDF сохранённых результатов

Общий слой отображает готовые строки анализа и срезов по [контракту 1.0](CONTRACT.md).
Он не запускает анализатор, derive_slices, их аналитические верификаторы, LLM,
сеть или чтение исходных журналов. Совпадение сигнатур не доказывает одинаковый
сценарий; изменение чисел не означает исправление или регрессию кода.

## Запуск

Установите `requirements-report.txt`. В примерах `python` — выбранный Python 3.10+.
Все пути CLI разрешаются относительно текущего каталога; код, схема и шрифты —
относительно каталога модуля. Прежний рабочий каталог не требуется.

```text
python tools/one_c_tj_report/build_report.py --analysis-dir /data/analysis --report-config /data/report.json --output /reports/overview.pdf
python tools/one_c_tj_report/build_trend_report.py --analysis-dir /data/analysis --slices-dir /data/slices --report-config /data/comparison.json --output /reports/comparison.pdf
python tools/one_c_tj_report/build_iteration_history_report.py --analysis-dir /data/analysis --slices-dir /data/slices --report-config /data/history.json --output /reports/history.pdf
```

Режимы требуют соответственно `report_kind`: `overview`, `comparison`, `history`.
Начните с отдельного примера нужного режима:
[overview.example.json](configs/overview.example.json),
[comparison.example.json](configs/comparison.example.json) или
[history.example.json](configs/history.example.json). Задайте название, дату
выпуска и нужные разделы. Примеры не содержат ID конкретной серии и работают с
любым совместимым комплектом. Дата выпуска не является датой замера.
`report_cli.py` также принимает любой из трёх режимов напрямую.
Параметры `--slices-dir` и `--overwrite` необязательны. Выход должен находиться
вне входных каталогов. Успех возвращает код 0, ошибка входа/рендера — 2.
`db_chatty_summary` выбирает сводку и покрытие без индивидуальных CALL,
`db_chatty_comparison` — только готовые изменения; полный раздел `db_chatty`
по-прежнему доступен, когда его детализация нужна в приложении.

## Две отдельные конфигурации

Конфигурация аналитики принадлежит `derive_slices`. В ней задаются набор срезов,
порядок и база замеров, минимальная выборка, пороги DB-chatty, цели и политика
APDEX, правила и пороги проблем. PDF получает только уже рассчитанные таблицы и
сохранённую эффективную конфигурацию из `slice_manifest.json`; исходный файл
аналитической конфигурации он не открывает.

Конфигурация представления принадлежит PDF. В ней допустимы название и пометка
документа, подписи точных ID, разделы, сортировка, top-N, единицы отображения,
округление и профиль поставляемого шрифта. Эти параметры не создают новые суммы,
средние, перцентили, доли, дельты, APDEX, базы сравнений или статусы проблем.
Рабочие примеры: [overview.example.json](configs/overview.example.json),
[comparison.example.json](configs/comparison.example.json) и
[history.example.json](configs/history.example.json).

Полный воспроизводимый smoke-проход по цепочке исходные синтетические журналы →
анализатор → отдельная проверка анализа → `derive_slices` → отдельные проверки
срезов → три PDF, включая команды из другого рабочего каталога и вариант одного
замера без срезов, описан в [examples/README.md](examples/README.md).

## Состав

| Файл | Ответственность |
|---|---|
| `schema_profile.json`, `report_schema.py` | Зафиксированный профиль версий, колонок, методов и типов |
| `report_input.py` | 21 обязательный файл анализа, необязательный манифест срезов и его CSV, хеши, ключи, ссылки, SQLite read-only |
| `report_config.py` | Только представление: разделы, точные ID, подписи, сортировка, top-N, единицы |
| `report_model.py`, `report_presentations.py` | Полные строки и разные компактные структуры overview/comparison/history; происхождение каждой ячейки сохраняется |
| `report_fonts.py` | Явная регистрация поставляемых кириллических шрифтов при рендере |
| `report_layout.py` | Экранирование текста, перенос длинных значений, страницы и атомарная публикация |
| `report_cli.py` | Единая командная строка трёх точек входа |

Поддерживаются только схема анализа **1.6**, анализатор **1.6.1**,
схема срезов **1.8**, расчётчик **1.8.0**, конфигурации **1.0** и закреплённые
подверсии правил. Срезы привязываются к хешам всех 21 файлов, `bundle_id`,
версиям и сохранённой конфигурации. Переименование версии не является миграцией.
Профиль обновляется отдельным изменением вместе с проверкой новых контрактов.

Нет среза — «не рассчитано»; валидная пустая таблица — «нет наблюдений»;
null/пустая ячейка — «показатель недоступен»; сохранённый признак неполноты —
«частичные данные». Ноль сохраняется нулём. Один замер допустим; базы сравнений
и дельты не создаются. Готовые причины и ограничения сохраняются в строках.

Основная часть использует компактные таблицы с русскими заголовками. Каждое
значение помечено ссылкой `V…`; индекс приложения показывает файл, безопасно
отображённый ключ строки, поле, исходное значение, единицу и состояние. После
индекса печатаются полные технические строки выбранных разделов с исходными,
неокруглёнными значениями. Для больших таблиц задавайте top-N явно:
по умолчанию показываются все строки.
Длинные списки ограничений в основной части сокращаются с указанием числа
скрытых элементов; ссылка `V…` раскрывает полный исходный список в приложении.
Сортировка и top-N истории выбирают заданное число уникальных траекторий; все их
сохранённые точки внутри окна выводятся в порядке `measurement_order`. Поэтому
число показанных строк истории может превышать top-N. Дата из ID не извлекается.
В overview при нескольких замерах top-N применяется отдельно к каждому замеру.
Параметры аналитики выводятся из манифеста, но не принимаются в настройках PDF.
Подписи `labels.operations` адресуют точные сохранённые `operation_id` или
сигнатуры; исходный ключ остаётся рядом с подписью. Это не идентификатор сценария.
Русская локаль — единственная поддерживаемая. Технические имена полей и
готовые статусы сохраняются для прослеживаемости.

Необязательный `document_notice` выводит заметную текстовую пометку на обложке,
не влияя на данные или аналитику.

Сравнение выводится отдельным блоком по `comparison_id`: стороны и N, база,
готовые значения и дельты, сопоставимость и ограничения. DB-chatty сохраняет
рядом порог, знаменатели и DB-покрытие, APDEX — обе цели, T, политику и
знаменатели. База за пределами отображаемого окна сохраняется. Общий APDEX
выводится отдельным блоком с полным составом по `overall_id` и покрытием той же
области/политики.
Итог с замерами вне окна исключается целиком; PDF не пересчитывает итог окна.
Покрытие области включает обе категории целей, а общий APDEX разделён по
`target_status`. Для `comparability`, `apdex_composition`, `apdex_coverage` и
`problem_rule_coverage` независимый top-N запрещён. Снимки `problem_registry`,
`problem_persisting`, `problem_unchecked` всегда относятся к последнему замеру
полного комплекта и снабжены этой подписью, включая выбор исторического окна.

`files`/`datasets` отбираются через принадлежность замеров наборам данных,
а не сравнением capture ID с actual measurement ID. Источники capture могут
охватывать несколько дней; их показатели не превращаются в итоги выбранного дня.
Ненаблюдавшиеся группы, отсутствующие цели и неопределённые проценты получают
готовую причину отсутствия значения. Флаги полноты и `error_summary` показаны
компактно в overview и повторены в приложении с путём к полю JSON. История
разделена по готовым `cohort_id` и `problem_id`; статусы проблем сопровождаются
сопоставимостью базы, причинами, ограничениями и покрытием правила.

Структурная проверка не доказывает математическую корректность показателей,
подлинность источника, полноту исходных ТЖ или сопоставимость сценариев.
Загрузчик читает все разрешённые файлы и проверяет их повторные хеши перед
публикацией; на больших комплектах это требует времени и памяти. Содержимое
детальных SQL/контекстов проверяется построчно и не удерживается для вывода.

Шрифты [Liberation Sans 2.1.5](assets/fonts/README.md) поставляются с SIL OFL 1.1.
Импорт модулей и `--help` не импортируют ReportLab и не регистрируют шрифты.
Данные и SQL экранируются как текст, включая похожие на HTML фрагменты.

## Проверки

Для тестов установите закреплённый набор, включающий ReportLab и `pypdf`:

```text
python -m pip install -r requirements-report-test.txt
python -B -m unittest discover -s tools/one_c_tj_report/tests -v
python -B -m unittest tools.one_c_tj_report.tests.test_producer_pipeline -v
```

Первая команда запускает все тесты PDF, вторая — отдельно полный producer-smoke
из временного каталога и с другим текущим рабочим каталогом для CLI.
Модульные фикстуры — небольшие искусственные сохранённые комплекты, включая
[зафиксированный выход текущих производителей](tests/fixtures/README.md); исходные журналы
и аналитический пересчёт не используются. Тестируются версии, обязательные
файлы, идентичность срезов, повреждения, пропуски, один замер, все три режима,
кириллица и сохранность результата при ошибке. Визуальное качество страниц
проверяется отдельно; эти тесты не подтверждают производительность полного
комплекта или работу на всех ОС.

Отдельный producer-проход из [examples/README.md](examples/README.md) строит все
JSON/CSV настоящими производителями из исходных `.log`. `verify_slices.py` при
этом повторно выполняет выбранные builders в своей проверке, но этот пересчёт не
входит в PDF-генератор. Успех малого синтетического набора не является замером
производительности или проверкой полного реального сбора.
