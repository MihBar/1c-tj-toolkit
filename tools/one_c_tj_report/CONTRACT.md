# Контракт универсального PDF-визуализатора

Версия контракта: **1.0**. Дата фиксации: **2026-09-03**.

Статус: нормативный контракт общего слоя визуализации.
`build_report.py`, `build_trend_report.py` и `build_iteration_history_report.py`
используют общий загрузчик, модель, конфигурацию и оформление.
Состав реализации и запуск описаны в [README.md](README.md).
Контракты анализатора и расчётчика не изменены.

## 1. Назначение и граница ответственности

Визуализатор отображает **готовые показатели, статусы и ограничения** из одного
сохранённого комплекта анализа и, при наличии, принадлежащего ему комплекта
`derive_slices`. Результат — PDF с прослеживаемым происхождением значений.
Название прикладной системы, пользователи, операции, SQL, даты и каталоги
не должны быть зашиты в коде визуализатора.

Разрешены:

- чтение разрешённых сохранённых файлов, проверка структуры, типов, ключей,
  ссылочной целостности, размеров и хешей;
- соединение готовых строк по точным идентификаторам без агрегации;
- выбор разделов и строк, сортировка, top-N, пагинация;
- локализация известных статусов без усиления их смысла;
- форматирование дат, единиц и округление только для вывода;
- технические сообщения «срез не предоставлен», «значение отсутствует» и
  сообщения об ошибке контракта.

Запрещены:

- чтение исходных ТЖ, архивов, их префиксов, прежних PDF и поиск других анализов;
- обращения к LLM, сети и внешним сервисам; выполнение SQL из входных данных;
- расчёт сумм, средних, перцентилей, долей, дельт, APDEX и аналитических рейтингов;
- определение превышений порога, приоритетов, полноты, сопоставимости,
  жизненного цикла проблем или связи CALL→SQL по эвристикам;
- пересчёт показателей при фильтрации, top-N, отсутствии или повреждении среза;
- экспертные заключения, рекомендации по исправлению, установление причин,
  решение о приёмке, исправлении кода, регрессии или готовности эксплуатации.

Подсчёт строк для проверки дескриптора файла и сообщение «показано X строк» —
технические операции. Подсчёт «всего проблем», «затронуто пользователей» или
«доля медленных CALL» — аналитика: такие карточки допустимы только при наличии
готового поля с определённой популяцией. Хеширование не является аналитическим
расчётом показателей.

| `sql_fingerprint_algorithm` | `sha256:1c-tj-sql-nul-version-nul-text:utf8` |
| `linkage_rules_version` | `legacy_end_longest/v1` |

Строки версий проверяются точно. Неизвестная версия отклоняется до публикации
PDF. Новая версия производителя требует явно документированного расширения
профиля; совпадение major/minor само по себе не разрешает её чтение.
Схемы анализа 1.1–1.5 не входят в этот профиль, хотя сам `derive_slices`
поддерживает 1.2–1.6. Переименование версии в JSON не является преобразованием
данных. Версии и определения полей сверяются с контрактами из раздела 12.

## 3. Входы и разрешённые файлы

Имена ниже соответствуют входам текущего общего CLI и трёх совместимых точек
запуска.

| Вход | Обязательность | Назначение |
|---|---|---|
| `analysis_dir` | Обязателен | Один сохранённый комплект анализа |
| `slices_dir` | Необязателен | Один комплект срезов именно этого анализа |
| `report_config` | Обязателен | JSON-конфигурация представления |
| `output` | Обязателен | Путь нового PDF вне входных каталогов |
| `overwrite` | По умолчанию `false` | Явное разрешение заменить существующий PDF |

Относительные пути входов разрешаются относительно каталога запуска; ссылки
в конфигурации представления — относительно её файла. После разрешения пути
фиксируются на весь запуск. Нет подразумеваемого рабочего каталога, поиска
«последнего результата» на диске или выбора соседнего комплекта.

### 3.1. Комплект анализа

Обязательны все 21 файл текущей схемы, даже когда разделы отображают только
агрегаты. Это проверка целостности комплекта, а не требование вычислять показатели
из деталей.

| Файлы | Роль |
|---|---|
| `analysis_metrics.json` | Версии, единицы, методика, counts, состояние публикации и обработки, готовые метрики |
| `datasets.csv`, `files.csv` | Наборы, интервалы, источники и зарегистрированные статусы |
| `operations.csv`, `identical_operations.csv` | Готовые операции и сравнения анализатора; не дополнительная популяция CALL |
| `heavy_sql.csv`, `errors.csv`, `locks.csv`, `linkage.csv` | Готовые показатели SQL, ошибок, блокировок и привязки |
| `call_observations.csv`, `top_calls.csv` | Сохранённые CALL и перекрывающееся представление top; не суммируются между собой |
| `analysis.sqlite`, `source_map.json` | Хранилище деталей и происхождение |
| `db_observations.csv`, `event_links.csv`, `link_candidates.csv` | DB-события и сохранённые решения о связях |
| `error_observations.csv`, `error_event_links.csv`, `error_link_candidates.csv`, `error_incidents.csv`, `error_incident_members.csv` | Ошибки, связи и версионированные гипотезы инцидентов |

Детали можно читать для структурной проверки и показа отдельных сохранённых
записей. Агрегировать их в визуализаторе нельзя. SQLite при необходимости
открывается только для чтения; SQL-тексты из данных никогда не исполняются.

### 3.2. Комплект срезов

Обязателен `slice_manifest.json` и каждый CSV, перечисленный в его
`selected_slices` / `outputs`. Разрешённые таблицы схемы 1.8:

| Группа | Имена без `.csv` |
|---|---|
| Качество | `data_quality` |
| Операции | `operation_history`, `operation_history_all_users`, `measurement_comparisons`, `comparability` |
| DB-chatty | `db_chatty`, `db_chatty_calls`, `db_chatty_fast_calls`, `db_chatty_duration`, `db_chatty_coverage`, `db_chatty_changes` |
| APDEX | `apdex`, `apdex_calls`, `apdex_uncovered`, `apdex_coverage`, `apdex_overall`, `apdex_composition`, `apdex_changes` |
| Проблемы | `problem_registry`, `problem_history`, `problem_improved`, `problem_persisting`, `problem_worsened`, `problem_new`, `problem_unchecked`, `problem_rule_coverage` |

Любое корректное подмножество допускается. Для `apdex_overall` обязательно
`apdex_composition`, как требует расчётчик. Отсутствие необъявленного среза
не является повреждением. Отсутствие объявленного файла — ошибка комплекта,
даже если его раздел выключен. Необъявленные файлы не читаются и не становятся
автоматической заменой отсутствующих срезов.

### 3.3. Граница доступа

Имена входных артефактов берутся из разрешённого набора, а не используются как
произвольные пути из JSON. Каждый фактически открываемый файл должен оставаться
в соответствующем каталоге после разрешения ссылок/junction; выход наружу
отклоняется. Посторонние файлы не сканируются.

`input_root`, `source`, `resolved_source`, `member` и расположения в `source_map`
— только строки происхождения. По ним запрещены даже `exists/stat`, а не только
чтение. Исходный файл аналитической конфигурации также не открывается: используется
сохранённая эффективная `configuration` из манифеста срезов.

Помимо указанных входов разрешены только явно настроенные/поставляемые шрифты.
Нет автоматической зависимости от системных Arial/DejaVu, переменной `WINDIR`,
картинок по URL или старого рабочего каталога. Отсутствие выбранного шрифта —
ошибка ресурса, а не повод молча заменить шрифт и изменить вёрстку.

## 4. Принадлежность анализа и срезов одному комплекту

Проверка выполняется до публикации PDF; входы не изменяются.

1. Проверить профиль версий, обязательные поля, типы и структуру файлов.
   JSON читается без повторных ключей и NaN/Infinity; CSV — с корректным
   заголовком, уникальными именами колонок и одинаковым числом полей в строках.
   Обязательные колонки определяются схемой, а не подставляются значениями
   по умолчанию. Проверить ключи и ссылки между используемыми представлениями.
2. Требовать `publication_state=complete` в анализе. Это состояние публикации,
   не утверждение о полноте исходных наблюдений. Проверить дескрипторы
   сохранённых артефактов, которые объявляет анализатор.
3. Для каждого из 21 файлов анализа получить SHA-256 точных байтов и размер.
   Составить объект `input_files`: имя файла → `{sha256, size_bytes}`.
   Его каноническая JSON-сериализация совпадает с `slice_config.canonical_json`:
   `ensure_ascii=False`, `sort_keys=True`, `separators=(",", ":")`,
   `allow_nan=False`, кодировка UTF-8, без добавочного перевода строки.
   SHA-256 этих байтов — `bundle_id`, как в `slice_input.load_bundle`.
4. При наличии срезов потребовать точное совпадение их `bundle_id` и
   `input_files` с вычисленным объектом. Перенос неизменённых файлов в другой
   каталог допустим; совпадение путей, дат или только source-set hash недостаточно.
5. Сверить `input_schema_version`, `input_analyzer_version`,
   `input_sql_normalization_version`, `input_linkage_rules_version`,
   `input_error_rules`, `recorded_source_set_hash_sha256` и
   `source_analysis_complete` с анализом. Проверить `population`:
   `primary=call_observations.csv`, ключ `[bundle_id, call_id]`, численность
   сохранённых строк; JSON и `top_calls` не являются дополнительными наблюдениями.
6. Проверить структуру сохранённой эффективной `configuration`, её версию и
   SHA-256 канонического JSON против `configuration_effective_sha256`.
   `expected_bundle_id`, если задан, должен совпадать. Проверить согласованность
   `configuration.slices`, `selected_slices` и `outputs`.
   `configuration_file_sha256` сохраняется как запись происхождения: исходный
   файл конфигурации заново не проверяется.
7. Для всех объявленных CSV срезов сверить SHA-256, размер, число строк без
   заголовка и колонки с `outputs`; проверить соответствие колонок профилю 1.8.
   Проверить ссылки на замеры и строковые ID в пределах заявленного scope.
   Фильтр выходных замеров может оставлять ссылки на базу вне отображаемого
   подмножества: такая база должна существовать в полном анализе.
8. Проверить неизменность входных байтов за время чтения/рендера. Если комплект
   изменился, PDF не публикуется. Ошибка не заменяется режимом «без срезов».

Эта проверка подтверждает структурную согласованность и принадлежность
сохранённых файлов. Она **не доказывает правильность аналитических расчётов,
подлинность источника или полноту ТЖ**. Совместно изменённые данные и хеши
не являются криптографически подписанным свидетельством.

Визуализатор не вызывает `derive_slices`, аналитические builders,
`verify_slices.verify` или `slice_input.load_bundle`: существующие пути загрузки
и верификации включают аналитические пересчёты. Структурные проверки при
реализации следует выделить без такого поведения. Полная независимая проверка
аналитики остаётся отдельным предварительным действием пользователя; сохранённые
`validation_checks` нельзя выдавать за заново выполненные проверки.

Без срезов вычисляется идентификатор анализа и проверяются доступные структурные
контракты; принадлежность срезов не оценивается. Вычисленный хеш не выдаётся за
сравнение с отсутствующим внешним эталоном.

## 5. Значения, единицы и происхождение

Для выводимого показателя сохраняются файл, ID/составной ключ строки, поле,
единица, scope, доступные числитель/знаменатель, численность наблюдений,
качество и ограничения. Для агрегатов анализатора без отдельного ID используется
их схемный составной ключ; для срезов — предоставленные `history_id`,
`comparison_id`, `problem_id`, `history_row_id`, `overall_id` и другие ID.
Представление не изменяет ключи при переименовании подписей.

| Поле / величина | Единица и отображение |
|---|---|
| Длительности `*_us`, включая `*_us_sum`, `avg_us`, `median_us`, `p95_us` | Микросекунды; разрешён перевод в мс/с с явным заголовком |
| `*_seconds*`, включая `db_seconds_per_call` | Секунды; не делить повторно на миллион |
| `*_bytes*`, memory / MemoryPeak | Байты; MiB = 1024² байт; знак сохраняется |
| `db_per_call` и аналогичные средние | Связанные DB-события на CALL, не секунды и не число SQL-семейств |
| Численность | Целое; точно сохранять смысл: события, CALL, группы, сигнатуры, пользователи |
| `*_percent` | Проценты 0–100 либо знаковая относительная дельта; не умножать ещё раз на 100 |
| Абсолютная дельта процентного показателя | Процентные пункты, не относительные проценты |
| APDEX | Безразмерное число 0–1; готовая абсолютная дельта — изменение шкалы 0–1 |
| `RowsAffected` | Значение счётчика ТЖ; не переименовывать в «прочитанные строки» |
| Временные метки | Сохранённое локальное время без timezone; часовой пояс неизвестен, если не задан источником |

Единица выбирается из явного словаря схемы, а не только по подстроке имени.
Например, `problem_*.metric_unit` и `metric` определяют смысл `value` и дельт.
Округление применяется после сортировки; запрещено определять статус по
округлённому значению. Суммы CALL/DB не переименовываются в длительность теста
или неперекрывающийся wall time. CPU%, остаток и overflow показываются только
как готовые показатели с их покрытием; PDF их не складывает и не вычитает.

Средние/перцентили разных пользователей и dataset не объединяются.
`same_user` и `all_users` — самостоятельные перекрывающиеся представления.
`affected_call_count` разных групп ошибок не суммируется; события ошибок,
затронутые CALL и `suspected_incident_count` не взаимозаменяемы.
TLOCK, TTIMEOUT и TDEADLOCK не объединяются под подписью TLOCK.

## 6. Конфигурация аналитики и представления

### 6.1. Только расчётчик

В аналитической конфигурации остаются `measurement_ids`,
`operations.measurement_order`, `series_baseline_measurement_id`, минимальный N,
пороги качества/DB-chatty, диапазоны длительности, определение быстрого CALL,
APDEX T/членство классов/статус цели/политика неуспеха, правила проблем и их
аналитические фильтры. Четыре базы операций — `series_baseline`,
`first_observation`, `previous_observation`, `previous_measurement` — не
переопределяются визуализатором. Базы `problem_*` также берутся из готовых полей.

Чтобы изменить перечисленное, пользователь отдельно запускает расчётчик и
передаёт новый комплект срезов. Визуализатор не открывает первоначальную
конфигурацию и не применяет к срезам собственные пороги.

### 6.2. Только представление

Нормативные поля конфигурации представления 1.0:

| Поле | Правило |
|---|---|
| `report_config_version` | Обязательно `1.0` |
| `report_kind` | `overview`, `comparison` или `history` |
| `title`, `locale`, `report_date` | Название; начальная локаль `ru-RU`; явная дата ISO, без скрытого `today()` |
| `document_notice` | Необязательная заметная пометка документа, например «синтетические данные» или «черновик»; только текст представления |
| `labels` | Отображения точных ID замеров, пользователей и операций в подписи; ключи и значения данных неизменны |
| `sections` | Упорядоченный список уникальных известных ID разделов |
| `tables` | Для ID таблицы: `sort` — список `{field, direction}`, `top_n` — положительное целое или `null` |
| `display_measurement_ids` | Необязательное подмножество существующих замеров для показа, не аналитический фильтр |
| `focus_measurement_id` | Необязательный точный ID для обзора; подпись «выбранный замер», не автоматически «последний» |
| `format` | Точность вывода, длительности `us/ms/s`, объёмы `bytes/MiB`, показывать ли provenance-пути и SQL-фрагменты |
| `fonts` | Поставляемый профиль regular/bold либо явные локальные ресурсы; без сетевого/системного автопоиска |

Неизвестные поля, разделы, сортировочные поля и ID отклоняются с указанием
причины. Аналитические параметры здесь недопустимы. Нет поля свободного
«экспертного заключения» и вставки произвольного HTML/исполняемых выражений.
Подписи экранируются; они не изменяют фиксированную семантику статусов и единиц.

Для таблицы без настройки сортировки сохраняется порядок входных строк.
Явная сортировка использует исходные значения, отсутствующие значения всегда
последние; при равенстве — точный стабильный ключ строки. `top_n=null` показывает
все строки. Ограничение строк не скрывает обязательные сведения о качестве,
scope и происхождении. Техническая подпись «показано X из Y строк» разрешена;
число строк не называется количеством независимых проблем/инцидентов.

## 7. Порядок замеров и сравнения

`measurement_id` — непрозрачный идентификатор. Нельзя извлекать дату из его
суффикса, имени каталога или пользовательской подписи. Capture и день не
объявляются независимыми экспериментами по строковому префиксу.

В истории операций/проблем используются готовые `measurement_order`,
`order_basis` и `series_order_reliable` соответствующего среза, а для проблем —
также `series_first_measurement_id` / `series_latest_measurement_id`.
В сравнениях обе стороны и база берутся из строки сравнения. Поля порядка
одной серии проверяются на согласованность между срезами этой серии.

`data_quality.measurement_order` в схеме 1.8 — отдельный порядок таблицы качества;
он не заменяет хронологию `OperationSeries`, учитывающую эффективную настройку
аналитики. Если есть только `data_quality`, он не даёт оснований восстановить
недостающие сравнения или выбрать аналитическую базу.

Если хронологический срез не предоставлен, доступны таблицы анализа в исходном
либо явно настроенном порядке представления. Такой порядок не обозначается
хронологией. При нескольких замерах без установленного порядка и без
`focus_measurement_id` обзор показывает их отдельными группами, не выбирая
«актуальный» автоматически. При единственном замере он является выбранным.

При `series_order_reliable=false` предупреждение сохраняется; не создаются
собственные относительные базы и дельты. Готовые значения/состояния расчётчика
показываются с его ограничениями. Фильтрация отображения не меняет полный порядок,
первое наблюдение, latest-снимок `problem_registry` и базы сравнений. База за
пределами показанных дат остаётся явно подписанной. Недостающие из-за фильтра
выхода срезов строки не восстанавливаются из CALL.

## 8. Отсутствующие значения и особые случаи

Пустая числовая CSV-ячейка и JSON `null` означают отсутствие значения. В PDF -
`-` и доступная причина. Известный ноль выводится как `0` с нужной точностью.
Пропущенная обязательная колонка, нечисловая строка в числовом поле и
NaN/Infinity — ошибка структуры, не допустимый пропуск.

| Ситуация | Обязательное поведение |
|---|---|
| Один замер | Обзор доступен; история — одна точка; сравнение показывает готовый статус отсутствия базы либо техническое сообщение об отсутствии строк сравнения |
| N=1 | Показывать готовые метрики и N; не утверждать повторяемость или надёжность p95; предупреждение о размере выборки брать из данных |
| Нет срезов | Показывать готовые строки анализатора; разделы срезов помечать «срез не предоставлен»; ничего не рассчитывать автоматически |
| Нет части срезов | Каждый раздел проверяет свои зависимости; остальные доступны; пропуск не скрывается |
| Объявленный срез отсутствует/повреждён | Отказ до публикации PDF, без подмены другим файлом или расчётом |
| Валидные пустые таблицы | Заголовки сохраняются; «в сохранённой таблице нет строк»; не «проблем нет» |
| Полностью пустой комплект | PDF с паспортом, готовыми counts и состояниями; без выдуманных замеров, метрик и заключений |
| SQL/ошибки есть, CALL нет | Показывать готовые SQL/ошибки и их measurement ID; отсутствие CALL не удаляет эти данные |
| Операция не наблюдалась | Сохранить готовый `not_observed`/эквивалентный статус; N=0 только если он задан; длительности, APDEX и дельты не заполнять |
| Нет T | «Цель не задана» по данным APDEX; не использовать значения прошлых отчётов; сохранить uncovered-популяцию |
| Нулевая база | Показывать готовую абсолютную дельту, если она есть; отсутствующий процент остаётся `—`, включая 0→0 |
| Счётчик частично доступен | Показывать готовое значение и numeric quality/охват; не делить сумму на полную популяцию и не корректировать по покрытию |
| Частичные источники | Сохранить наблюдения и ограничения; не исключать их молча и не объявлять исходный сбор полным |
| Неизвестный статус | Ошибка несовместимого контракта; не заменять «нормой», «нет проблем» или произвольной категорией |

`publication_state`, `analysis_complete`, `source_processing_complete` и
`collection_completeness` показываются раздельно. Завершённая публикация
совместима с частичной обработкой; успешная обработка не доказывает полноту
сбора. Качество capture не превращается в качество отдельного дня/операции;
процент DB-linkage замера не является уверенностью связи конкретного CALL.
При отсутствии готового предупреждения визуализатор сообщает лишь отсутствие
сведения, а не устанавливает качество самостоятельно.

## 9. Разделы и источники показателей

Это реестр разделов для `sections`; вид отчёта определяет подачу, а не формулы.

| ID раздела | Источник и обязательные ограничения |
|---|---|
| `provenance` | Версии, хеши, effective configuration и состояния комплектов; обязателен для всех видов |
| `sources` | Готовые строки `files`, `datasets`; без собственной сводки статусов |
| `quality` | `data_quality`; при его отсутствии только готовые флаги анализа с подписью scope |
| `operations` | В обзоре `operations.csv` как dataset-агрегаты; в истории `operation_history`; эти популяции не подменяют друг друга |
| `operations_all_users` | Только `operation_history_all_users`; перекрывается с same-user, не суммируется |
| `comparisons` | `measurement_comparisons` + `comparability`; обе стороны, N, база, известные различия и неизвестные условия обязательны |
| `db_chatty` | Выбранные готовые `db_chatty*` таблицы; отдельные пороги/популяции и знаменатели; для изменений — ID обеих сторон |
| `db_chatty_summary` | Только `db_chatty` + `db_chatty_coverage` для компактного обзора; расчёты не повторяются |
| `db_chatty_comparison` | Только готовый `db_chatty_changes` для сравнительного отчёта |
| `apdex` | `apdex` + `apdex_coverage`; `apdex_uncovered` для детализации отсутствующих целей; T, статус цели, failure policy и scope обязательны |
| `apdex_overall` | `apdex_overall` + `apdex_composition` + `apdex_coverage`; не среднее APDEX строк и не смесь статусов целей |
| `apdex_changes` | `apdex_changes`; обе стороны, цели, N и ограничения из готовых строк |
| `problems` | `problem_registry` + `problem_rule_coverage`; состояние правила отдельно от направления изменения |
| `problem_history` | `problem_history` + `problem_rule_coverage`; готовая история, без самостоятельного восстановления отсутствий |
| `problem_views` | Предоставленные `problem_improved/persisting/worsened/new/unchecked`; представления перекрываются, не суммируются |
| `sql` | `heavy_sql.csv`: готовые метрики, структурные флаги, sample/normalized SQL; без классификации семейств и выводов об EXPLAIN |
| `errors` | `errors.csv` и готовый `error_summary` анализа; числа разных групп не суммируются |
| `locks` | `locks.csv` с сохранением типа события и контекста; без вердикта о причине задержек |

`overview` предназначен для готовых текущих показателей выбранного замера,
`comparison` — готовых сравнительных строк, `history` — готовых рядов и статусов.
При недоступных зависимостях выбранного раздела выводится техническая причина.
Нет требования к фиксированному числу страниц или к определённой серии.
Дополнительные индивидуальные таблицы CALL/DB/APDEX можно показывать только как
сохранённые строки; новые агрегированные разделы требуют отдельного контракта
данных производителя.

## 10. Допустимый язык статусов

Совпадение сигнатуры, в том числе вместе с пользователем, **не подтверждает
одинаковый сценарий**. Роль, документ, параметры, объём данных, нагрузка,
версии приложения/платформы, cold/warm и бизнес-результат остаются неизвестными,
если это указано производителем. Пользователь не переименовывается в роль.

Готовые числовые статусы переводятся буквально: «показатель снизился»,
«показатель вырос», «порог превышен», «ниже порога в наблюдениях»,
«не наблюдалось», «недостаточно данных». Названия `problem_improved` и
`problem_worsened` не разрешают писать «исправлено» и «регрессия кода».
Первое превышение — первое наблюдение в сохранённой серии, не дата появления
дефекта. Отсутствие события и значение ниже порога не доказывают исправление.

Не допускаются автоматически сформированные заключения «блокировки не ведущие»,
«SQL-механизм исправлен», «производительность не принимать», «ограниченная
эксплуатация допустима» и подобные решения. Готовые инженерные приоритеты
анализатора не превращаются в бизнес-SLA. APDEX относится к зарегистрированным
серверным CALL, не к end-to-end отклику; статус согласования цели — декларация
аналитической конфигурации, а не независимо подтверждённое согласование.

## 11. Проверяемые требования к реализации

- Любая фактическая цифра и аналитический статус имеют источник до поля и
  строки; техническое форматирование не создаёт новый показатель.
- Произвольная серия не требует изменения Python-кода; нет фильтров по старым
  именам, датам, путям, сигнатурам и SQL-fingerprint.
- Перемещение неизменённого комплекта не меняет принадлежность; смешение
  файлов разных комплектов и подмена объявленного CSV приводят к отказу.
- Один замер, отсутствие срезов, пустой согласованный комплект и частичные
  источники обрабатываются по разделу 8.
- Нули, пропуски и неопределённые проценты визуально различимы.
- Показ подмножества, сортировка и top-N не меняют значения, знаменатели,
  базы и статусы; обязательные ограничения остаются видимыми.
- Нет сетевых запросов, LLM, доступа к provenance-путям и аналитических
  пересчётов, в том числе через вспомогательные загрузчики/верификаторы.
- Ошибка входа не повреждает существующий PDF; публикация происходит только
  после успешной проверки входов и завершения рендера.
- Один набор поставляемых шрифтов обеспечивает кириллицу без системного
  поиска. Длинные ID, SQL и произвольное число замеров не требуют фиксированной
  ручной пагинации. Побайтовая идентичность PDF этим контрактом не обещается.

Это нормативные критерии приёмки. Само наличие функции или теста не доказывает
выполнение критерия; результат фиксируется только конкретной проверкой.

## 12. Основная часть и техническое приложение

`report_kind` задаёт структуру основной части, а не аналитический алгоритм.
Основная часть выбирает и переставляет готовые поля; техническое приложение
автоматически сохраняет полные строки выбранных разделов и манифесты с исходными,
неокруглёнными значениями. Каждое
фактическое значение основной части имеет ссылку на индекс с точными
`source_file`, ключом строки, полем, исходным сохранённым значением, единицей,
состоянием и причиной отсутствия. Статические русские заголовки не являются
аналитическими значениями. Длинный список ограничений, различий или неизвестных
условий может быть сокращён только визуально: ссылка `V…` и приложение сохраняют
полное исходное значение.

### 12.1. Overview

Сначала показываются область отчёта, отдельные флаги полноты из
`analysis_metrics.json`, готовый `data_quality`, его период наблюдений и
ограничения. При отсутствии `data_quality` флаги манифеста остаются в основной
части, а сам срез получает состояние «не рассчитано». Затем идут сохранённые
показатели операций, SQL, ошибок и блокировок; bundle-level `error_summary`
показывается отдельно от строк `errors.csv`. Пустая таблица сохраняет заголовок
и состояние «нет наблюдений». Сортировка и top-N
определяют порядок показа; слово «медленные» не вводит отдельного порога PDF.
При нескольких замерах top-N применяется отдельно к каждому точному
`measurement_id`, чтобы один замер не вытеснил остальные. Готовые APDEX,
DB-chatty и проблемные срезы выводятся дополнительными компактными таблицами,
только если они предоставлены и включены в конфигурацию. Каждый выбранный
`apdex_overall` образует отдельный блок с полным связанным
`apdex_composition` и покрытием той же области.

### 12.2. Comparison

Каждый готовый `comparison_id` образует один блок: операция и пользователь,
тип базы, опорный и текущий замеры, N и статус наблюдения обеих сторон,
состояния сравнения и выборки; затем строки
готовых значений `reference/current/delta_absolute/delta_percent`; рядом —
`comparability_status`, известные различия, неизвестные условия и ограничения.
Соединение выполняется только по проверенному `comparison_id`. Аналогичная
проекция разрешена для готовых `db_chatty_changes` и `apdex_changes`. Для
DB-chatty рядом остаются готовые порог, оператор, знаменатели и DB-покрытие;
для APDEX — обе цели и T, статусы и источники целей, `target_match`, знаменатели,
`failure_policy` и область оценки. Пустая дельта не восстанавливается из двух
значений. Предоставленный пустой сравнительный срез означает «нет наблюдений»;
отсутствующий — «не рассчитано».

### 12.3. History

История операций группируется по готовому `cohort_id`, история числовых проблем
— по `problem_id`. Все точки выбранной траектории остаются видимыми в порядке
готового `measurement_order`. Top-N означает число уникальных траекторий, а не
число отдельных строк; он не обрезает последующие точки выбранной траектории.
Для проблемы рядом показаны значение, порог, `threshold_status`, опорный замер,
готовые дельты, отдельный `change_status`, сопоставимость базы, известные
различия, неизвестные условия, ограничения и готовое `problem_rule_coverage`.
Порядок не восстанавливается из даты или текста `measurement_id`.

`focus_measurement_id` применим только к `overview`; в остальных режимах это
ошибка конфигурации. Если список разделов не задан, используются разные
представительские наборы по умолчанию для overview, comparison и history.

Русские заголовки и перевод единиц относятся к оформлению. В основном тексте
допустим буквальный перевод технических enum без экспертного переосмысления.
Фразы о совпавшем пользовательском сценарии, доказанном исправлении или
регрессии кода запрещены. Исходные enum остаются видимыми в приложении.

Уточнения реализации представления: для связанных `comparability`,
`apdex_composition`, `apdex_coverage`, `problem_rule_coverage` независимый top-N
недопустим. Их строки следуют за выбранными основными строками по проверенным
ключам. Общий APDEX с областью, выходящей за отображаемое окно, исключается
целиком. Состав показанного итога не сокращается; покрытие относится ко всей
его области и может включать обе категории целей. Отсутствующий срез покрытия
помечается как «не рассчитано», не заменяется пустой выборкой.

Для истории сортировка и top-N выбирают начальные строки траекторий; все
сохранённые точки выбранных траекторий внутри окна остаются видны в порядке
`measurement_order`. Снимки последнего замера полного комплекта не фильтруются
как исторические строки и явно подписываются. Выбор источников через dataset
не меняет их исходный capture scope. Никакое из этих действий не пересчитывает
аналитические значения или статусы.
