# Запуск и проверка анализатора ТЖ

Анализатор **1.6.1**, схема результата **1.6**, SQLite **1.1**, верификатор **1.2.0**.
Python 3.10+, только стандартная библиотека. Копируйте **весь** каталог
`one_c_tj_analyzer`: нужны модули `.py`, обе схемы `.sql` и конфигурации.
Исходники читаются без изменений; PDF и текстовые диагнозы не создаются.
Для готового комплекта переходите сразу к проверке и [SLICES_RUNBOOK.md](SLICES_RUNBOOK.md).

## Обычный запуск

PowerShell: замените пути и ID конкретного захвата. Эти команды описывают
будущий прогон, их наличие в инструкции не означает выполненный анализ.

```powershell
# Выполняйте команды из корня проекта.
$TjPython = 'python'
$TjTools = Join-Path $PWD 'tools\one_c_tj_analyzer'
$TjInput = 'C:\Path\To\1clogs'
$TjOutput = Join-Path $PWD 'data\analysis\run_002'

if (-not (Test-Path -LiteralPath $TjInput -PathType Container)) { throw 'Нет входного каталога' }
& $TjPython -B "$TjTools\analyze_1c_tj.py" $TjInput `
    --output-dir $TjOutput --capture-id 'capture-2026-09-03-example' `
    --archive-mode auto --top-calls 500
$TjParseCode = $LASTEXITCODE
if ($TjParseCode -notin @(0, 4)) { throw "Ошибка разбора: $TjParseCode" }
```

Каждому прогону нужен отдельный выход. `--overwrite` разрешает замену явно;
для сравнения лучше сохранить оба результата. Полное хеширование несжатых
источников обязательно; `--hash-sources` оставлен как совместимый параметр.

Для переноса исходников или повторного анализа копий передайте прежний
`--source-map`. Одновременный `--capture-id` должен совпадать с картой.
Без карты и явного ID захват выводится из абсолютного пути; перенос без
карты меняет идентичность. Не анализируйте дописываемую выгрузку.

## Архивы, копии и повреждения

Поддерживаются `.log`, ZIP, TAR, TAR.GZ, TGZ, `.log.gz`, вложенные каталоги
и одинаковые имена членов архива (различаются порядковым номером).
Символические ссылки, junction и другие reparse points внутри входного дерева
не обходятся и не читаются, даже если их цель находится внутри дерева. Сам
переданный корень сначала разрешается штатными средствами ОС. Исключены выход, `analysis_data`, `analysis_output`,
`.git`, `node_modules`, `__pycache__`; дополнительно доступен `--exclude-dir`.

Ресурсные границы применяются до или во время чтения без молчаливого усечения:

- не более 10 000 членов в одном ZIP/TAR;
- не более 2 ГиБ несжатых данных в одном `.log` или члене архива;
- не более 16 ГиБ заявленных `.log`-данных суммарно в одном ZIP/TAR;
- не более 16 МиБ в одной записи ТЖ, включая многострочную запись.

Превышение отражается как пропуск/ошибка источника и делает результат неполным.
Архивы не извлекаются на диск. Если легитимный журнал превышает границу,
разделите его на отдельные журналы до анализа, сохранив исходный комплект.

- `auto` пропускает архив, если найдены loose `.log` под соседним каталогом
  с именем архива без суффикса. Это эвристика, а не доказательство полной
  распаковки; проверяйте `archive_inventory`.
- `always` читает архивы и loose-файлы. Копии учитываются один раз только
  при одной логической идентичности в карте и совпадающем полном SHA-256.
  Одинаковые байты независимых источников не удаляются.
- `never` предназначен для явно выбранной полной распакованной выгрузки.
- `--salvage-nul-prefix` сохраняет законченные UTF-8-записи до NUL, исключая
  последнюю потенциально оборванную запись. Итог остаётся частичным.
  Без флага NUL-файл целиком пропускается.

Пустой файл и точный UTF-8 BOM без записей — нематериальные пропуски.
Произвольные короткие байты не считаются пустым файлом. Повреждённые архивы,
ошибки чтения/декодирования и недоступные каталоги отражаются в `files.csv`,
`warnings` и/или `analysis.sqlite.parse_issues`. Закрытые паролем ZIP и
неподдерживаемые методы сжатия дают диагностируемую ошибку чтения.
`.7z`, `.rar`, `.tar.xz`, `.bz2`, `.zst` и архивы внутри архивов не распознаются:
подготовьте их отдельно, сохранив оригиналы.

## Формат результата

Схема 1.6 содержит **21 обязательный файл**:

| Часть | Файлы |
|---|---|
| Манифест и сводки | `analysis_metrics.json`, `files.csv`, `datasets.csv`, `operations.csv`, `identical_operations.csv`, `heavy_sql.csv`, `errors.csv`, `locks.csv`, `linkage.csv`, `top_calls.csv`, `call_observations.csv` |
| Полные DB и источники | `analysis.sqlite`, `source_map.json`, `db_observations.csv`, `event_links.csv`, `link_candidates.csv` |
| Ошибки и гипотезы | `error_observations.csv`, `error_event_links.csv`, `error_link_candidates.csv`, `error_incidents.csv`, `error_incident_members.csv` |

CSV — UTF-8 с BOM, запятая, NULL — пустая ячейка. Длительности и `*_time_us` —
микросекунды. Абсолютное время локальное, без придуманной часовой зоны;
неизвестное время обозначается явно. Все DBPOSTGRS и EXCP/QERR сохраняются,
включая несвязанные и DB без SQL. Полные SQL находятся в `sql_texts`.
`top_nested_sql` ограничен десятью шаблонами только для показа, `--top-calls`
тоже ограничивает только превью. Они не заменяют первичную популяцию.

Поле CSV ограничено 16 МиБ во всех штатных загрузчиках и верификаторе;
превышение отклоняется, а не обрезается. CSV является точным машиночитаемым
свидетельством и не обезвреживает значения, начинающиеся с `=`, `+`, `-` или
`@`. При открытии в табличном редакторе импортируйте все текстовые колонки как
текст и не разрешайте выполнение внешних ссылок или формул.

Контракты: [счётчики](NUMERIC_CONTRACT.md), [SQL](SQL_NORMALIZATION.md),
[события](EVENT_DETAIL.md), [ошибки](ERROR_DETAIL.md). В `errors.csv` прежний
`linked_call_count` заменён на `linked_error_event_count`, `affected_call_count`;
гипотезы считаются в `suspected_incident_count`. Уникальные CALL и гипотезы
по сигнатурам неаддитивны; общий итог — `error_summary`. Причина и инициатор
отмены не устанавливаются по одному сообщению.

## Проверка результата

```powershell
$TjVerifyText = & $TjPython -B "$TjTools\verify_analysis.py" --analysis-dir $TjOutput
$TjVerifyCode = $LASTEXITCODE
$TjCheck = $TjVerifyText | ConvertFrom-Json
$TjCheck | ConvertTo-Json -Depth 20
if ($TjVerifyCode -ne 0) { throw 'Согласованность результата не подтверждена' }

Import-Csv -LiteralPath (Join-Path $TjOutput 'files.csv') |
    Group-Object status | Select-Object Count, Name
Import-Csv -LiteralPath (Join-Path $TjOutput 'linkage.csv') |
    Select-Object measurement_id, dbpostgrs_linked_count_percent, error_linked_count_percent
```

`PASS` и код 0 подтверждают согласованность **сохранённых свидетельств**.
Отдельно изучите `observation_state=complete|partial|empty` и `completeness`:
полноту обработки, неизвестное время, статусы файлов, предупреждения и коды
`parse_issues`. Даже `complete` не доказывает полный сбор системы:
`collection_completeness` остаётся `unknown`. Счётчики и CPU оценивайте вместе
с `numeric_quality` и покрытием; пропуски не превращаются в нули.
Верификатор 1.2.0 не рассчитывает бизнес-метрики, не классифицирует операции по
названиям предметной области и не задаёт цели APDEX. Такие правила применяются
только расчётчиком срезов по явно переданной конфигурации.

Для 1.5/1.6 проверяются уникальность ID независимо от объявленных ограничений
БД, ссылки, позиции записей, SQL-словарь без потерянных/лишних элементов,
числовые состояния и популяции, решения CALL и однократное включение в суммы.
Median/p95/p99 SQL, блокировок и событий наборов пересчитываются по отдельным
длительностям. CALL и объединённые сравнения считаются по наблюдениям, а не
по средним перцентилей групп. p95/p99 — nearest-rank; median при чётном N —
полусумма центральных значений. Сортировку событий выполняет SQLite.
В 1.6 также проверяются все ошибки, уникальные CALL, членство, версии и основания
гипотез. Подмена агрегата при согласованных CSV/JSON и обновлённых хешах
отклоняется, если он расходится с детализацией. Исходные журналы не открываются;
соответствие их реальных байтов сохранённым хешам этим не доказывается.

## Проходы и ошибки

В 1.6.1 источники хешируются при инспекции и один раз читаются в события.
Все последующие расчёты, включая SDBL и блокировки, используют SQLite.
Повторного чтения журналов при агрегировании нет; выбор CALL не менялся.

При сбое чтения сохраняются законченные записи. `analyzed_bytes` — граница
последней такой записи, а не размер буфера. Причина неполноты сохраняется
в `inspection_read_error`/`ingestion_read_error` и статусе источника.
Ошибка обхода — `discovery_error`. Замена содержимого между инспекцией
и успешным чтением обнаруживается по хешу и останавливает прогон.

Сбой SQLite, экспорта или проверки не выдаётся за успешный результат.
В I/O-диагностике SQLite/экспорта указан этап. Комплект строится и проверяется
во временном каталоге, манифест публикуется последним. Ошибка до публикации
сохраняет прежний результат. Сбой во время замены может оставить неполный
комплект, который проверка контрольных сумм отклонит.

Коды парсера: `0` — записан результат, в том числе `partial`; `2` — ошибка
параметров/обработки; `4` — пригодных источников нет, диагностика записана;
`5` — непустой выход без `--overwrite`. Фатальная ошибка проверки также
завершает CLI ненулевым кодом. Код 0 парсера не заменяет верификацию.
Верификатор возвращает 0 для PASS, ненулевой код для FAIL/ERROR. Комплект
при коде 4 парсера можно проверить, но использовать как замер нельзя.

## Совместимость

| Потребитель | Поведение |
|---|---|
| `verify_analysis.py` 1.2.0 | Принимает 1.2–1.6; для 1.5/1.6 полная сверка наблюдений. Для 1.3/1.4 точны CALL, SQL/блокировки имеют только проверки ограничений агрегатов. Ветка 1.2 также проверяет наличие записанных путей источников. Бизнес-пороги и APDEX не рассчитываются |
| `derive_slices.py` 1.8.0 | Вход 1.2–1.6, выход 1.8; строгий комплект и версии; bundle ID 1.6 включает 21 файл |
| `verify_slices.py`, `audit_stage1.py` | Работают через строгий загрузчик; исходные журналы не читают |
| Универсальный PDF-визуализатор | Только анализ 1.6 / анализатор 1.6.1 и необязательные срезы 1.8 / расчётчик 1.8.0; старые и неизвестные версии отклоняются. Конфигурации аналитики и представления разделены |

Старые результаты не мигрируются и не получают новые значения инцидентов
автоматически. Не меняйте `schema_version` для обхода ограничения потребителя.
Неизвестные версии, смешение SQL fingerprints и новых правил ошибок со
старой схемой отклоняются. В патче 1.6.1 формат 1.6 и версии нормализации/
связывания сохранены: усилены проверки и исправлена диагностика неполноты.
Ранее записанный комплект может перестать проходить проверку, если содержит
обнаруженное несоответствие.

Воспроизводимый малый проход от синтетических исходных `.log` через анализатор,
отдельные проверки, `derive_slices` и три PDF приведён в
[примерах PDF](../one_c_tj_report/examples/README.md). Он проверяет интеграцию
текущих CLI, но не производительность и память на полном реальном объёме.

## Перед новым прогоном

```powershell
& $TjPython -B -m unittest discover -s "$TjTools\tests" -b
if ($LASTEXITCODE -ne 0) { throw 'Синтетические проверки не пройдены' }
& $TjPython -B "$TjTools\analyze_1c_tj.py" --version
```

Тесты охватывают повреждения, пропуски, архивы/копии, этапы чтения, неизвестное
время, подмену данных и повторяемость файлов. Они подтверждают готовность
к контролируемому прогону на фиксированной копии, но не время выполнения
и пик памяти на полном реальном объёме. События и сортировки используют диск;
прежние CALL, агрегаты и списки длительностей ещё остаются в памяти. Нужен
запас места под SQLite/CSV и временные сортировки; жёсткого общего лимита RAM нет.
