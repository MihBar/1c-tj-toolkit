# Первый этап: запуск и приёмочная проверка сохранённых результатов

Расчётчик **1.8.0**, выходная схема **1.8**, входные схемы Анализатора ТЖ **1.2/1.3/1.4/1.5/1.6**, конфигурация **1.0**. Независимый проверочный скрипт `audit_stage1.py` — **1.1.0**. Все программы используют Python 3.10+ и стандартную библиотеку.

Этот этап работает только с уже сохранённым комплектом CSV/JSON. Он не читает исходные ТЖ/архивы, не меняет парсер, не генерирует PDF, не использует сеть или LLM. Он не восстанавливает отсутствующие наблюдения и не доказывает причины изменения быстродействия.

## 1. Вход и подготовка

Вход — один каталог схемы 1.2–1.4 со всеми 11 файлами либо схемы 1.5 со всеми 16 файлами, либо схемы 1.6 со всеми 21 файлом. Счётчики и их знаменатели: [NUMERIC_CONTRACT.md](NUMERIC_CONTRACT.md). Версии SQL и fingerprints: [SQL_NORMALIZATION.md](SQL_NORMALIZATION.md). Полная детализация: [EVENT_DETAIL.md](EVENT_DETAIL.md).

Состав комплекта:

```text
analysis_metrics.json
call_observations.csv
top_calls.csv
files.csv
datasets.csv
operations.csv
identical_operations.csv
heavy_sql.csv
errors.csv
locks.csv
linkage.csv
```

Рекурсивного поиска здесь нет: указывается именно каталог готового комплекта, не корень логов. Дополнительные файлы не являются источниками наблюдений. `call_observations.csv` — единственная популяция CALL; JSON, агрегаты и `top_calls.csv` используются для сверки и метаданных. Один CALL нельзя повторно добавлять из этих представлений.

Для продолжения истории передавайте комплект, содержащий всю нужную серию. История не объединяется с прежними PDF или старым реестром проблем. Если старого замера нет во входе, его показатели не выдумываются.

Выполняйте команды из корня проекта. Замените `python` на путь к своему интерпретатору, если он отсутствует в PATH:

```powershell
$TjToolDir = ".\tools\one_c_tj_analyzer"
$TjPython = "python"
$TjSaved = ".\data\analysis\run_001"
$TjConfig = "$TjToolDir\configs\stage1.full.example.json"
$TjOutput = ".\output\my_stage1_run_001"

& $TjPython -B "$TjToolDir\derive_slices.py" --version
& $TjPython -B "$TjToolDir\derive_slices.py" --list-slices
& $TjPython -B "$TjToolDir\derive_slices.py" --list-problem-metrics
```

`stage1.full.example.json` выбирает все 26 таблиц. Его пороги проблем и DB-chatty — явно обозначенные диагностические предложения, не утверждённые нормы или SLA. T намеренно не заданы. Перед реальным изменением конфигурации сохраните отдельную копию и укажите её путь; прежний результат оставьте неизменным.

## 2. Проверка без записи и полный запуск

```powershell
& $TjPython -B "$TjToolDir\derive_slices.py" `
  --analysis-dir $TjSaved --config $TjConfig --validate-only
if ($LASTEXITCODE -ne 0) { throw "Проверка сохранённого комплекта не прошла" }

& $TjPython -B "$TjToolDir\derive_slices.py" `
  --analysis-dir $TjSaved --config $TjConfig --output-dir $TjOutput
if ($LASTEXITCODE -ne 0) { throw "Срезы не сформированы; прочитайте сообщение об ошибке" }
```

`--validate-only` проверяет вход, конфигурацию и возможность построить выбранные срезы; это не только быстрая проверка заголовков. На больших комплектах он может занимать примерно столько же времени, сколько сам расчёт. Выходные файлы не создаются.

Выход и вход должны быть раздельными каталогами, без вложения друг в друга. Конфигурация не должна лежать внутри выходного каталога. По умолчанию непустой выходной каталог отклоняется.

`--overwrite` означает явное разрешение заменить только распознанный результат текущей выходной схемы с тем же составом срезов. Чужие файлы, вложенные папки или ссылки приводят к отказу. Не используйте этот флаг для старых результатов другой версии — задайте новый каталог. Даже при разрешённой перезаписи частично прерванный запуск необходимо проверить верификатором.

## 3. Только выбранные срезы

Список после `--slices` передаётся **через пробел**, не через запятую. Он заменяет список из конфигурации, остальные настройки сохраняются.

```powershell
& $TjPython -B "$TjToolDir\derive_slices.py" `
  --analysis-dir $TjSaved --config $TjConfig `
  --output-dir "C:\Path\To\selected_run_001" `
  --slices data_quality operation_history measurement_comparisons comparability

& $TjPython -B "$TjToolDir\derive_slices.py" `
  --analysis-dir $TjSaved --config $TjConfig `
  --output-dir "C:\Path\To\problems_run_001" `
  --slices problem_registry problem_history problem_improved problem_persisting problem_worsened problem_new problem_unchecked problem_rule_coverage

& $TjPython -B "$TjToolDir\derive_slices.py" `
  --analysis-dir $TjSaved --config $TjConfig `
  --output-dir "C:\Path\To\apdex_run_001" `
  --slices apdex apdex_coverage apdex_overall
```

При выборе `apdex_overall` автоматически добавляется обязательный `apdex_composition`. Непокрытые T операции не получают APDEX.

`measurement_ids` в конфигурации — `null` для всей серии либо список точных ID. Отбор ограничивает строки, но не переопределяет базовый замер и поиск предыдущего наблюдения. Реестр проблем и актуальные выборки продолжают оценивать последний замер **всего** комплекта. Для нового независимого набора проблем задайте другой `problems.series_id`; для продолжения той же серии сохраняйте его.

## 4. Изменение порогов и T

Настройки независимы; изменение порога DB-chatty само по себе не меняет уже заданное правило истории проблем:

| Блок | Что меняется |
|---|---|
| `db_chatty.thresholds` | Пороги K отдельных CALL: `db_count > K`; пример `[100,500,1000,5000]` |
| `db_chatty.fast_call_max_seconds` | Быстрый CALL: длительность ≤ границы; пример `1` |
| `db_chatty.duration_bounds_seconds` | Верхние включительные границы диапазонов; пример `[1,5,10,30]` |
| `data_quality.min_call_count` | Предупреждение о размере выборки замера |
| `data_quality.db_linkage_warning_percent` | Предупреждение о покрытии DB → CALL по замеру, не гарантия точности отдельной связи |
| `operations.min_comparison_count` | Предупреждение о малом N сравнения; числовая дельта при малом N не запрещена |
| `apdex.min_call_count` | Предупреждение о малом N APDEX; значение при N>0 и заданном T всё равно вычисляется |
| `problems.rules[].min_call_count` | Фильтр пригодности для статуса/сравнения данной проблемы; сырое первое превышение не удаляется |
| `problems.rules[].threshold`, `operator` | Явное правило `>` или `>=`, в единицах выбранной метрики |
| `problems.rules[].db_events_threshold` | Внутренний K для DB-chatty-правила, отдельно от внешнего порога количества/доли/максимума |

Для проблем также доступны точные фильтры `signatures`/`users`, `require_clean_sources`, минимальные проценты покрытия DB. Полный контракт: [PROBLEMS_RUNBOOK.md](PROBLEMS_RUNBOOK.md).

Пример структуры T, **не готовое согласованное значение для эксплуатации**:

```json
"apdex": {
  "targets": [
    {
      "signature": "ТОЧНАЯ_СИГНАТУРА_ИЗ_APDEX_UNCOVERED_CSV",
      "t_seconds": 2,
      "status": "engineering_proposal",
      "source": "Основание инженерного предложения; не согласованный SLA"
    }
  ],
  "classes": [],
  "min_call_count": 10,
  "failure_policy": "latency_only",
  "confirmed_failures": {"bundle_id": null, "calls": []}
}
```

Вместо цели операции можно задать класс с `class_id`, явным списком `signatures`, `t_seconds`, `status`, `source`. Точная цель операции имеет приоритет над классом. Роль, имя функции или префикс автоматически классом не становятся. Неизвестные сигнатуры/двойное членство класса отклоняются.

`business_approved` используйте только при действительном утверждении цели бизнесом, указав основание в `source`. Программа не проверяет подлинность этого решения. Без T APDEX и категории пусты; это не нулевой APDEX.

APDEX = `(2S + A)/(2N)`: S — `d ≤ T`, A — `T < d ≤ 4T`, неудовлетворительные — `d > 4T`. Ровно T и 4T проверяются в целых микросекундах. При `latency_only` EXCP не превращается автоматически в неуспех. Для подтверждённых неуспехов нужна политика `confirmed_failures_frustrated`, точный `bundle_id`, существующие `call_id` и явные основания. Подробности: [APDEX_RUNBOOK.md](APDEX_RUNBOOK.md).

Одна конфигурация целей применяется ко всей серии; это сравнение при одинаковых текущих T, не реконструкция исторических SLA.

## 5. Выходные файлы

CSV — UTF-8 с BOM, запятая, пустая ячейка означает отсутствующее значение; массивы и объекты внутри ячеек — JSON. Не заменяйте пустые значения нулями при импорте. `*_us` — микросекунды, объёмы/MemoryPeak — байты, `*_percent` — шкала 0–100, APDEX — 0–1. Точные дроби float не округляются для последующих расчётов.

| Группа | Таблицы |
|---|---|
| Качество — 1 | `data_quality` |
| Операции — 4 | `operation_history`, `operation_history_all_users`, `measurement_comparisons`, `comparability` |
| DB-chatty — 6 | `db_chatty`, `db_chatty_calls`, `db_chatty_fast_calls`, `db_chatty_duration`, `db_chatty_coverage`, `db_chatty_changes` |
| APDEX — 7 | `apdex`, `apdex_calls`, `apdex_uncovered`, `apdex_coverage`, `apdex_overall`, `apdex_composition`, `apdex_changes` |
| Проблемы — 8 | `problem_registry`, `problem_history`, `problem_improved`, `problem_persisting`, `problem_worsened`, `problem_new`, `problem_unchecked`, `problem_rule_coverage` |

Каждое имя — отдельный `.csv`. При отсутствии строк сохраняется заголовок. `slice_manifest.json` содержит версии, фактическую конфигурацию и её хеш, SHA-256 всех входных и выходных файлов, ID комплекта, список проверок, ограничения методики и число строк каждой таблицы. Манифест публикуется последним.

Для анализа текущей истории начинайте с `problem_registry.csv`. Первая проблемная база и последний замер сохранены отдельно. В `problem_history.csv` видны промежуточные состояния. Снижения/увеличения в отдельных выборках — переходы по каждой базе, не число независимых дефектов; для текущих переходов фильтруйте `is_latest_series_measurement=true`.

Полный комплект может быть объёмным: высокая доля строк описывает отсутствие операции, различные базы и пороги. Пользовательские сводки и все пользователи, замеры и вся серия, вложенные пороги и пять выборок проблем — пересекающиеся представления, их нельзя суммировать.

## 6. Проверки результата

Для любой выбранной комбинации срезов:

```powershell
& $TjPython -B "$TjToolDir\verify_slices.py" `
  --analysis-dir $TjSaved --slices-dir $TjOutput
if ($LASTEXITCODE -ne 0) { throw "Результат не прошёл воспроизведение" }
```

Верификатор повторно рассчитывает значения из сохранённого комплекта, сверяет байты, порядок строк, хеши и конфигурацию. Исходный файл конфигурации ему не нужен — используется сохранённая эффективная конфигурация. Старые результаты требуют соответствующей версии расчётчика; в текущую схему они автоматически не мигрируются.

Дополнительная независимая числовая сверка полного набора:

```powershell
& $TjPython -B "$TjToolDir\audit_stage1.py" `
  --analysis-dir $TjSaved --slices-dir $TjOutput
```

`audit_stage1.py` выводит JSON в консоль и ничего не записывает. Он использует загрузчик/валидатор входа, но независимо вычисляет контрольные CALL-метрики, перцентили, базы, знаменатели, APDEX и правила истории проблем. Он проверяет все 26 таблиц, а не произвольный выбранный поднабор. Текущий контракт аудита: полный набор замеров с сохранёнными временами CALL. Не применяйте PASS одного набора к другому. Обычный `verify_slices.py` поддерживает выборки.

Для отдельной проверки воспроизводимости запустите `derive_slices.py` дважды с одним входом и **тем же файлом конфигурации**, но двумя новыми выходными каталогами. Все 26 CSV и манифест должны совпасть по SHA-256. Путь выходного каталога не влияет на содержимое файлов. Изменение форматирования файла конфигурации изменяет его записанный хеш, даже если числа и каноническая эффективная конфигурация остаются прежними.

Тесты только первого этапа, без тестов парсера ТЖ:

```powershell
& $TjPython -B -m unittest discover -s "$TjToolDir\tests" -p "test_*slice*.py" -v
& $TjPython -B -m unittest discover -s "$TjToolDir\tests" -p "test_stage1_audit.py" -v
```

Тестовые константы относятся к синтетическим наблюдениям, не к реальным измеренным результатам. Проверочный тест APDEX с искусственным T подтверждает арифметику, но не создаёт T для эксплуатационного комплекта.

## 7. Ошибки и безопасное поведение

| Ситуация | Действие |
|---|---|
| Нет файла, неизвестная схема/единицы, повреждён CSV/JSON | Код завершения 2, JSON `ERROR` расчётчика/верификатора или `FAIL` независимого аудита; передайте полный корректный сохранённый комплект. Не подставляйте пустой файл. |
| Дубликат CALL ID, противоречие CSV и JSON, неверные суммы/хеши | Остановитесь и установите происхождение комплекта. Не исправляйте числа вручную ради прохождения проверки. |
| Неизвестная сигнатура, замер, T, правило или неоднозначный класс | Исправьте конфигурацию по точным сохранённым идентификаторам. Ноль вместо отсутствующего T не допускается. |
| Неоднозначная хронология | История проблем не строится; при наличии обоснования задайте `operations.measurement_order` всеми ID ровно по одному. Иначе ограничьтесь срезами без относительной истории. |
| Каталог результата занят, пересекается с входом или содержит чужие файлы | Выберите новый отдельный каталог. Не удаляйте исходные данные и старые отчёты. |
| Недостаточно прав/места, прерванный запуск | Исправьте внешнюю причину; не используйте непроверенный результат. Новый запуск — в новый каталог, затем верификация. |
| Изменился вход или конфигурация во время расчёта | Запуск отклоняется. Обеспечьте неизменный комплект и повторите в новый каталог. |
| `source_analysis_complete=false` | Это ограничение первоначального сбора, не автоматически ошибка текущего расчёта. Допустимые числа рассчитываются, неполнота сохраняется в манифесте и качестве. |

Не включайте вызов парсера или создание PDF как автоматический fallback. Недостаток информации, требующий новых ТЖ, относится к отдельному запросу.

## 8. Ограничения интерпретации

- Это зарегистрированные серверные CALL, не бизнес-транзакции и не end-to-end пользовательский отклик. Суммы CALL/DB/CPU не являются независимыми слагаемыми чистого времени эксплуатации.
- Равенство сигнатуры и пользователя — не равенство роли, документа, данных, параметров, cold/warm или нагрузки. Некоторые сигнатуры (`Background job`, общие платформенные операции) сами по себе слишком широки для отождествления бизнес-сценария; дополнительное разделение не выдумывается.
- Пропуск — «не наблюдалось», не ноль и не исправление. Предыдущий замер и предыдущее наблюдение различаются. Процент при нулевой базе пустой; малое N и неизвестные параметры сохраняются.
- Ограничение нумерации: `data_quality.measurement_order` локален для выбранных замеров и основан на временах CALL; операции/проблемы используют порядок полной серии и могут учитывать явный `operations.measurement_order`. Связывайте таблицы по `measurement_id`, не по порядковому номеру. На проверенном полном комплекте временные порядки совпали.
- Входная схема не различает некоторые отсутствующие/невалидные счётчики и ноль. Нулевой DB/CALL не доказывает отсутствие обращений. Процент DB → CALL — покрытие зарегистрированных событий на уровне замера, не правильность каждой связи и не полнота журнала.
- DB-chatty — числовой профиль. Пороги не доказывают избыточность или N+1. Изменение числа высокоплотных CALL может отражать рост N без роста их доли.
- APDEX без T не рассчитывается. Смена состава операций меняет общий APDEX без изменения отдельных операций; состав обязателен. EXCP не является автоматическим доказательством бизнес-неуспеха.
- Проблема — карточка правила, а не независимый дефект. Первое наблюдение не датирует появление в коде. Статусы порога и направления изменений отдельны; «исправлено», «регрессия кода» и «причина доказана» не присваиваются.
- Проверки доказывают согласованность и воспроизводимость чисел в сохранённом комплекте. Они не проверяют корректность бизнес-расчётов, целостность данных, безопасность и причинный эффект изменений кода.

Первый этап не включает повторный парсинг, новую нормализацию SQL, восстановление полной связи CALL → SQL или обновление PDF. Эти действия требуют отдельного запроса.
