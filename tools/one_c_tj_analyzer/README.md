# Детерминированный анализатор технологического журнала 1С

`analyze_1c_tj.py` версии 1.6.1 выполняет только вычислительную часть анализа. Скрипт не обращается к LLM, не генерирует диагностические формулировки и не создаёт PDF. Он читает исходные журналы, рассчитывает метрики и сохраняет машиночитаемые SQLite/JSON/CSV.

Обычный запуск, проверка результата, диагностика неполноты и совместимость потребителей: [RUNBOOK.md](RUNBOOK.md). Для установки нужен весь каталог модулей и схем, а не один скрипт.

Числовая схема **1.3** различает корректные, отсутствующие, пустые, некорректные и выходящие за диапазон счётчики. Неизвестные числа сохраняются как null; средние используют доступные наблюдения, CPU% — их же CALL duration. Полный контракт: [NUMERIC_CONTRACT.md](NUMERIC_CONTRACT.md).

Текущая схема **1.6** сохраняет эту числовую семантику и нормализацию SQL **2.0**: [SQL_NORMALIZATION.md](SQL_NORMALIZATION.md). Полная детализация DBPOSTGRS, словарь SQL и основания связи с CALL сохраняются в SQLite и дополнительных CSV: [EVENT_DETAIL.md](EVENT_DETAIL.md).

Скрипт не изменяет исходные журналы и использует только стандартную библиотеку Python 3.10+.

## Отдельные срезы без повторного чтения ТЖ

Единая инструкция первого этапа: [STAGE1_RUNBOOK.md](STAGE1_RUNBOOK.md). Полная конфигурация — `configs/stage1.full.example.json`; дополнительная независимая числовая проверка всех срезов — `audit_stage1.py`.

Для работы **с уже сохранённым комплектом SQLite/CSV/JSON** добавлен независимый расчётчик `derive_slices.py` версии 1.8.0. Он не вызывает парсер, не читает исходные журналы/архивы и не создаёт PDF. Принимает `--analysis-dir`, `--config`, `--output-dir`, поддерживает `--slices`, `--validate-only` и явный `--overwrite` только для собственного результата.

Доступны `data_quality`, `operation_history`, `operation_history_all_users`, `measurement_comparisons`, `comparability`. История строится из отдельных CALL, без усреднения перцентилей групп; пропуски сохраняются. Четыре базы сравнения раздельны: общая база серии, первое наблюдение пары операция–пользователь, предыдущее наблюдение и непосредственно предыдущий замер. Сводка всех пользователей вынесена отдельно. Схемы входа — 1.2, 1.3, 1.4, 1.5 и 1.6; единственный источник наблюдений CALL — `call_observations.csv`. Пример полного запуска: `configs/operations.example.json`.

Полный порядок запуска, конфигурация, контракт данных и тесты: [SLICES_RUNBOOK.md](SLICES_RUNBOOK.md). Проверка срезов — `verify_slices.py`; проверка входного комплекта встроена в общий строгий загрузчик и доступна отдельно через `verify_analysis.py`.

Самостоятельный блок DB-chatty: `db_chatty` (средние групп и фактические превышения CALL), `db_chatty_calls`, `db_chatty_fast_calls`, `db_chatty_duration`, `db_chatty_coverage`, `db_chatty_changes`. Пример отдельного запуска — `configs/db_chatty.example.json`. Пороговые значения 100/500/1000/5000 настраиваются и являются только диагностическим профилем, не нормативами и не доказательством избыточности. Полная детализация CALL → SQL доступна в схеме 1.5; срезы DB-chatty по-прежнему используют счётчики CALL, N+1 не диагностируется.

APDEX по зарегистрированным серверным CALL: `apdex`, `apdex_calls`, `apdex_uncovered`, `apdex_coverage`, `apdex_overall`, `apdex_composition`, `apdex_changes`. Конфигурация `configs/apdex.example.json` намеренно не содержит T: без явно заданной цели операция остаётся непокрытой. Инженерные предложения и бизнес-утверждённые цели отделены; общий показатель нельзя экспортировать без состава выборки. Формула, политика подтверждённых неуспехов и запуск: [APDEX_RUNBOOK.md](APDEX_RUNBOOK.md).

История числовых проблем: `problem_registry`, `problem_history`, `problem_improved`, `problem_persisting`, `problem_worsened`, `problem_new`, `problem_unchecked`, `problem_rule_coverage`. Она сохраняет проблемы первого замера, добавляет поздние и не смешивает направления разных показателей. Пример правил — `configs/problems.example.json`; каталог метрик — `--list-problem-metrics`. Статусы не означают исправление, регрессию кода или установленную причину. Подробности: [PROBLEMS_RUNBOOK.md](PROBLEMS_RUNBOOK.md).

## Быстрый запуск парсера исходных ТЖ

```powershell
python .\analyze_1c_tj.py "C:\Path\To\1clogs" `
  --output-dir "C:\Path\To\analysis_data\run_001" `
  --capture-id "capture-2026-09-03-example" `
  --archive-mode auto
```

Если команда `python` не зарегистрирована в `PATH`, укажите полный путь к `python.exe`:

```powershell
& "C:\Path\To\Python\python.exe" .\analyze_1c_tj.py `
  "C:\Path\To\1clogs" `
  -o "C:\Path\To\analysis_data\run_001" `
  --capture-id "capture-2026-09-03-example" `
  --archive-mode auto
```

Путь к каталогу журналов является обязательным позиционным параметром. В коде нет предопределённого каталога, пользователя, даты или списка замеров.

## Что обнаруживается автоматически

- `.log` на любой глубине вложенности;
- стандартные процессные каталоги `rphost_*`, `ragent_*`, `rmngr_*`, `ras_*`;
- пользователь из поля `Usr`, а не из имени папки;
- фактическая дата и час из стандартного имени файла `YYMMDDHH.log`, минуты и секунды — из события;
- отдельные наборы данных по корню выгрузки над процессным каталогом;
- фактические срезы замеров вида `<верхний каталог>@YYYY-MM-DD`, чтобы не смешивать разные календарные дни внутри ошибочно названной папки;
- многострочные события;
- пустые файлы и трёхбайтовые BOM-маркеры;
- повреждённые файлы с NUL-байтами;
- ZIP, TAR, TAR.GZ, TGZ и одиночные `.log.gz`.

В режиме `--archive-mode auto` архив не разбирается, если рядом существует распакованный одноимённый каталог с `.log`; полнота распаковки не доказывается. Для чтения обоих нужен `--archive-mode always`. Объединение копий требует карты `--source-map` с одинаковой логической идентичностью и совпадения полного SHA-256; одного совпадения байтов недостаточно. Все несжатые источники теперь хешируются всегда. Записи читаются непосредственно из архива без изменения исходного каталога.

## Результаты

В выходном каталоге создаются:

| Файл | Содержание |
|---|---|
| `analysis_metrics.json` | Полный набор рассчитанных метрик и описание методики |
| `analysis.sqlite` | Отдельные события, полный SQL-словарь, решения о CALL и все кандидаты |
| `source_map.json` | Логическая идентичность источников для повторного использования |
| `db_observations.csv` | Все DBPOSTGRS без ограничения top-N, с SQL-ссылкой, временем, счётчиками и Context |
| `event_links.csv`, `link_candidates.csv` | Решения о связывании и полное основание выбора |
| `files.csv` | Инвентаризация файлов, статус разбора и повреждения |
| `datasets.csv` | Фактические окна, пользователи, процессы и типы событий |
| `operations.csv` | Статистика каждой CALL-сигнатуры по набору и пользователю |
| `identical_operations.csv` | Сигнатуры, встречающиеся минимум в двух замерах |
| `heavy_sql.csv` | Нормализованные DBPOSTGRS-запросы и их статистика |
| `errors.csv` | EXCP/QERR: события, уникальные затронутые CALL и предполагаемые инциденты по сигнатурам |
| `locks.csv` | TLOCK/TTIMEOUT/TDEADLOCK |
| `linkage.csv` | Полнота временной привязки DBPOSTGRS/SDBL/ошибок/блокировок к CALL |
| `top_calls.csv` | Самые долгие отдельные CALL для технических паспортов |
| `call_observations.csv` | Все отдельные CALL для точного APDEX и повторной проверки распределений |

CSV записываются в UTF-8 с BOM, разделитель — запятая. Числовые поля остаются числами; длительности хранятся в микросекундах. Для перевода в секунды значение нужно разделить на `1_000_000`.

В схеме 1.6 добавлены пять полных CSV ошибок, связей и предполагаемых инцидентов; всего 21 файл. Глобальные distinct-итоги находятся в `error_summary`, строки сигнатур неаддитивны. Контракт: [ERROR_DETAIL.md](ERROR_DETAIL.md).

## Рассчитываемые метрики CALL

Для каждой комбинации `dataset + user + CALL signature` рассчитываются:

- N, сумма, average, median, p95, p99, minimum и maximum;
- число вызовов не короче 1, 5, 10 и 30 секунд;
- CpuTime и CPU/wall;
- Memory total/average/maximum и распределение MemoryPeak;
- DBPOSTGRS на вызов, DB time на вызов и maximum DBPOSTGRS на один CALL;
- RowsAffected, InBytes, OutBytes и MemoryPeak;
- TLOCK и ошибки, попавшие во временное окно CALL;
- коэффициент вариации, нижняя граница неатрибутированного времени и переполнение неаддитивных счётчиков;
- тяжёлые вложенные SQL;
- детерминированный кандидат P0/P1/P2. Это инженерная сортировка, а не согласованный бизнес-SLA.

DBPOSTGRS связывается с CALL только при совпадении набора, серверного процесса, пользователя и `OSThread`, а время события должно находиться внутри интервала CALL. При наличии `SessionID` ему отдаётся предпочтение. Если интервалов несколько, выбирается самый длинный содержащий CALL. Правило явно записывается в JSON и воспроизводится при повторном запуске. Доля связанного числа и времени DBPOSTGRS публикуется в `linkage.csv`; нулевой DB/call нельзя интерпретировать без проверки этого покрытия.

SDBL не суммируется с CALL как независимое wall time.

## Нормализация SQL

Версия 2.0 разбирает полный SQL на токены. Временные таблицы перенумеровываются с сохранением повторных ссылок; JOIN двух таблиц отделён от self-JOIN. Литералы и комментарии не влияют на поиск отношений; физические имена, поля и структура выражений сохраняются. Fingerprint включает версию, `sample_sql` используется только для показа. Неоднозначный текст получает явный статус `raw_fallback`. Правила, ограничения, изменения формата и проверки: [SQL_NORMALIZATION.md](SQL_NORMALIZATION.md). Конкретный индекс или узел плана скрипт не диагностирует: для этого нужен EXPLAIN.

## Сравнение замеров

`identical_operations.csv` строится по комбинации `CALL signature + user` после точной агрегации всех поднаборов одного замера. Порядок определяется фактическим временем первого CALL, а не именем каталога. Для count, average, median, p95, maximum, DB/call, DB seconds/call, CPU% и OutBytes/call сохраняются абсолютные и процентные изменения.

Даже совпадение сигнатуры и пользователя не доказывает одинаковые роль, документ, параметры, данные и cold/warm-состояние. Поэтому такие строки получают уровень сопоставимости B; совпадение только сигнатуры при разных пользователях — C. Это кандидаты на контролируемое сравнение, а не автоматическое доказательство регрессии.

## Параметры

```text
input_dir                 обязательная папка журналов
-o, --output-dir PATH     каталог результата; по умолчанию <input>/analysis_data
--archive-mode MODE       auto | always | never
--exclude-dir NAME        исключить имя каталога; можно повторять
--hash-sources            совместимый параметр; SHA-256 источников считается всегда
--capture-id ID           постоянный идентификатор исходного сбора
--source-map PATH         карта логических источников и доказанных копий
--salvage-nul-prefix      взять только завершённые UTF-8-записи до бинарной/NUL-порчи
--top-calls N             число отдельных CALL в top_calls.csv; по умолчанию 200
--overwrite               разрешить замену файлов в непустом выходном каталоге
--version                 версия анализатора
```

По умолчанию исключаются каталоги `analysis_output`, `analysis_data`, `.git`, `node_modules` и `__pycache__`, а также сам выходной каталог.

## Обработка пограничных случаев

- Путь отсутствует или указывает на файл: сообщение в `stderr`, код возврата 2.
- В каталоге нет пригодных журналов: создаются диагностические `analysis_metrics.json` и CSV, код возврата 4.
- Выходной каталог непустой без `--overwrite`: обработка не начинается, код возврата 5.
- Один файл повреждён: без специального флага он получает статус `skipped`; с `--salvage-nul-prefix` анализируется только доказуемо текстовый префикс до повреждения, последняя потенциально незавершённая запись и весь хвост отбрасываются. Статус — `partial_nul_salvaged`, а `analysis_complete` остаётся `false`.
- `skipped_duplicate` получают только копии одного логического источника с одинаковым SHA-256; все физические места сохраняются в SQLite.
- Нестандартное имя `.log`: события разбираются, но абсолютное время помечается недоступным.
- Повреждённый архив: ошибка заносится в `warnings`, остальные источники продолжают обрабатываться.
- Недоступный каталог или сбой инспекции/чтения: причина сохраняется в `warnings` и/или `parse_issues`, итог помечается неполным. При сбое чтения учитываются только законченные записи; произвольные короткие файлы не считаются пустыми.
- Неверная дата в имени файла: события сохраняются с неизвестным абсолютным временем, `absolute_timestamps_complete=false`.
- После сохранения событий источники повторно не читаются: SDBL и блокировки также агрегируются из SQLite. Сбой SQLite/экспорта останавливает публикацию с указанием этапа; до публикации прежний результат сохраняется.
- Один замер: создаётся полный анализ текущего состояния, а `identical_operations.csv` остаётся без искусственного сравнения.

## Воспроизводимость

В JSON нет текущего времени запуска. Сортировка, median, nearest-rank p95/p99, нормализация и правила связи событий фиксированы. При одинаковых байтах источников, пути и параметрах содержимое результата одинаково. Для переноса сбора используйте сохранённый `source_map.json`. Статусы связей, источник ID и ограничения памяти описаны в [EVENT_DETAIL.md](EVENT_DETAIL.md).

Календарный интервал между первым и последним событием сохраняется как `calendar_span_seconds`, но не трактуется как чистая продолжительность теста.

Сверка уже созданного набора выполняется скриптом `verify_analysis.py` версии 1.2.0. Для схемы 1.5/1.6 он проверяет уникальность ID независимо от ограничений SQLite, целостность ссылок, позиции и полноту популяций, весь SQL-словарь, покрытие счётчиков, суммы и отсутствие двойного счёта. Median/p95/p99 CALL, SQL, блокировок и событий наборов пересчитываются по отдельным длительностям; объединённые сравнения не усредняют перцентили групп. В 1.6 проверяются также исходные ошибки, уникальные CALL и версионированные гипотезы инцидентов:

```powershell
python .\verify_analysis.py --analysis-dir "C:\Path\To\analysis_data\run_001"
```

Успешная проверка возвращает `"status":"PASS"` и код `0`. Полнота отражается отдельно в `observation_state` и `completeness`: согласованный частичный или пустой комплект тоже получает PASS. Полноту сбора ТЖ это не доказывает. Современные комплекты проверяются без чтения исходников; историческая ветка 1.2 дополнительно проверяет наличие записанных путей. Верификатор не применяет названия предметной области, бизнес-пороги или цели APDEX; они задаются только в конфигурации расчётчика срезов.

Верификатор и расчётчик срезов принимают схемы 1.2–1.6. Текущий универсальный PDF-визуализатор принимает только анализ 1.6 / анализатор 1.6.1 и необязательные срезы 1.8 / расчётчик 1.8.0; остальные версии и смешение fingerprints отклоняются. Патч анализатора 1.6.1 сохраняет схему 1.6 и правила связывания, усиливает проверку и исправляет диагностику чтения; ранее скрытая несогласованность старого результата теперь может быть отклонена. Полный producer-проход до трёх PDF описан в [интеграционном примере](../one_c_tj_report/examples/README.md).

Детализация и временные сортировки хранятся на диске. CALL, агрегаты и часть списков длительностей пока остаются в памяти; жёсткого общего лимита RAM нет. Синтетические тесты не подтверждают время выполнения и расход памяти на полном реальном объёме.
