# События ошибок, затронутые CALL и предполагаемые инциденты

Анализатор **1.6.1**, схема комплекта **1.6**, SQLite **1.1** (`user_version=2`).
Это расширение [контракта событий](EVENT_DETAIL.md). Область ошибок — все
распознанные **EXCP и QERR**. TLOCK/TTIMEOUT/TDEADLOCK остаются в блокировках;
текст внутри DBPOSTGRS сам по себе не порождает дополнительное событие ошибки.

## Форматы и идентичность

К 16 файлам схемы 1.5 добавлены пять обязательных CSV; полный комплект — 21 файл.

| Файл / таблица SQLite | Контракт |
|---|---|
| `error_observations.csv` / `error_observations` | Ровно одна строка на EXCP/QERR, включая несвязанные события и события без сообщения |
| `error_event_links.csv` / `error_link_decisions` | Одно решение о CALL на событие, с версией, основанием, выбранным CALL и числом кандидатов |
| `error_link_candidates.csv` / `error_link_candidates` | Все кандидаты, сеанс/соединение, покрытие интервала и основание выбора или исключения |
| `error_incidents.csv` / `error_incidents` | Одна предполагаемая группа: ID, версия, ключ, представитель, число событий, уникальных CALL, первое/последнее время |
| `error_incident_members.csv` / `error_incident_members` | Одно членство на событие; ID группы, правило, причина, роль сообщения, полный JSON оснований |

`events` содержит исходную запись; `error_events` — её ошибочную часть;
`suspected_incidents` — ключи гипотез. CSV записываются в UTF-8 с BOM,
NULL — пустая ячейка. Времена `start_time_us`/`end_time_us` — микросекунды
наивного локального времени относительно 1970-01-01, без придуманной зоны.
`raw_timestamp` и `time_state` сохраняют неполноту времени.

Каждая ошибка содержит `event_id`, `source_id`, `source_version_id`,
`byte_start`/`byte_end`, номер записи и строки, SHA-256 исходной записи,
ссылку `source`, тип, длительность, время, пользователя и исходный `Usr`,
процесс, поток, сеанс, ConnectID, **полный Context**, атрибуты и сигнатуру.
Числовые поля всех событий доступны в `numeric_values`. Физические пути,
имя и порядковый номер элемента архива находятся в `source_locations`.
Координаты относятся к исходным несжатым байтам; механизм устойчивых ID
`event/v1` из схемы 1.5 не изменён.

Сообщение выбирается из первого непустого `Descr`, `Description`, `DBMS`;
если все пусты — из первого присутствующего поля. `message_field`,
`message_state=present|empty|missing` и полный `raw_message` сохраняются.
Все исходные поля сообщений также остаются в `attributes_json`.
SQL не считается текстом ошибки: `Sql` сохраняется через `sql_text_id`
в общем словаре `sql_texts`, включая QERR без сообщения. Такой SQL не
создаёт DB-наблюдение и не увеличивает DB-суммы.

## Три разных счётчика

Глобальные итоги находятся в `analysis_metrics.json.error_summary`:

| Поле | Определение |
|---|---|
| `event_count` | Число отдельных EXCP/QERR |
| `linked_error_event_count` | Число событий с выбранным CALL |
| `unlinked_error_event_count` | Число событий без выбранного CALL |
| `affected_call_count` | `COUNT(DISTINCT selected CALL event_id)` |
| `suspected_incident_count` | `COUNT(DISTINCT incident_id)`, включая одиночные группы |
| `ambiguous_linked_error_event_count` | События с несколькими допустимыми CALL и сохранённым прежним владельцем |
| `fallback_linked_error_event_count` | События со статусом `linked_by_rule` |

В `counts` даны также `error_events`, `affected_calls`, `suspected_incidents`.
`affected_call_count` означает CALL, затронутые **по правилу связывания**,
включая неоднозначные и резервные назначения. Это не число доказанно
неуспешных бизнес-операций. Одно событие увеличивает `CALL.error_count`
ровно один раз, у выбранного владельца; во внешние CALL счётчик не переносится.

В `errors.csv` и JSON `errors[]` прежний `linked_call_count` удалён:
он фактически считал события, несмотря на название. Теперь есть
`linked_error_event_count` и `affected_call_count`. Неявный `incident_count`
заменён на `suspected_incident_count` с `incident_rules_version`.
Ключ строки — `(measurement_id, event, signature_id)`. `sample` и `category`
берутся из события с минимальным `event_id` внутри группы.

**Distinct-счётчики строк неаддитивны.** CALL с разными ошибками встречается
в нескольких сигнатурах; обёртка EXCP и сообщение QERR могут войти в одну
гипотезу. Группа может пересечь границу суток внутри одного CALL.
Для общего итога используйте `error_summary`, а для произвольного среза —
`COUNT(DISTINCT ...)` по отфильтрованным первичным событиям и их членству.
`event_count = linked_error_event_count + unlinked_error_event_count`.

## Версии и основания

`error_signature_version=full_message/v2`: свёртка пробелов, абстрагирование
UUID, дат и многозначных чисел выполняются над **полным сообщением**,
без прежних ограничений 4000/1800 символов. Версионированный SHA-256
`signature_id=H(error-signature/v2, version, message_state, signature)`
различает пустое и отсутствующее сообщение. `sample` — только превью
до 2400 символов. Сигнатура служит сводке и **не является ключом инцидента**.

`error_linkage_rules_version=legacy_end_longest_error/v1` воспроизводит
прежний выбор ошибки → CALL: тот же dataset, пользователь, процесс и
OSThread; `CALL.start ≤ error.end ≤ CALL.end`; совпадающий непустой SessionID
предпочтителен; затем максимальная длительность CALL и минимальный старый
`call_id`. ConnectID диагностический. Статусы: `linked_unique`,
`linked_by_rule`, `ambiguous`, `unlinked`. Полное описание записано в
`error_linkage_rules`; DB-версия `legacy_end_longest/v1` не менялась.

`incident_rules_version=same_call_exact_payload/v1`:

1. Требуется **однозначная** связь `linked_unique`, непустые пользователь,
   процесс, поток, SessionID и полный Context, непустое сообщение,
   отсутствие конфликта ConnectID с CALL.
2. В тексте только CRLF/CR заменяются на LF и убираются внешние пробелы.
   Повторно снимаются только точные ведущие обёртки из `incident_rules.wrappers`
   (полный список также находится в [error_rules.py](error_rules.py)).
   Например, `Ошибка выполнения запроса:\n` или
   `Ошибка при вызове метода контекста (Выполнить)\nпо причине:\n`.
3. Ключ включает конкретный CALL ID, dataset, пользователя, процесс, поток,
   сеанс, ConnectID, хеш **полного Context** и хеш точного остатка сообщения.
   Регистр, внутренние пробелы, числа, UUID и неизвестные обёртки сохраняются.
   Хеши получаются SHA-256 с отдельными доменами идентичности.
4. Неоднозначная/резервная связь, отсутствие CALL, идентификаторов, Context
   или сообщения создают отдельную группу на каждое событие. Эти записи
   не теряются и не объединяются между собой.
5. Временного окна нет. Близость во времени не используется как основание.
   Даже одинаковое сообщение в одном CALL может отражать разные причины:
   группа обозначает только **предполагаемый** общий инцидент.

`incident_id` — SHA-256 домена, версии и полного ключа; для одиночной группы
ключом служит `event_id`. Для фиксированных исходных событий, CALL и версии
результат детерминирован. Членство хранит `reason_code`, `message_role`,
снятые обёртки, область совпадения и качество связи. Для допустимого ключа
`same_call_exact_payload` группа может пока содержать одно событие;
реальное объединение отражается числом членов > 1.

Категория вроде `statement_cancelled` — только совпадение текстового маркера.
`hypothesis_status=unconfirmed`, `root_cause=NULL`, `cancellation_initiator=NULL`.
Текст «user request» не устанавливает человека, сервис или механизм отмены.
Обёртка не устанавливает корневую причину.

## Проверка и потребители

Перед публикацией валидатор повторно вычисляет сигнатуры из сохранённых
полных полей, каждое решение и кандидатов, каждый ключ/ID гипотезы и её
основания; сверяет покрытия, PK/FK, суммы CALL, уникальные счётчики,
сводки, хеши и CSV-зеркала. Каждая ошибка имеет ровно одно решение
и одно членство; пустые группы недопустимы. Исходные журналы для проверки
и расчётчика не открываются. Подмена версии, членства или evidence отклоняется.

Схемы 1.2–1.5 продолжают загружаться с прежними именами и исторической
семантикой; их старые оценки не пересчитываются и не объявляются новыми
гипотезами. Неизвестные версии и старые имена счётчиков в новом `errors.csv`
отклоняются. Расчётчик **1.8.0**, срезы **1.8**, принимает 1.2–1.6 и сохраняет
`input_error_rules`. Bundle ID схемы 1.6 включает все 21 файл. Универсальный
PDF-визуализатор принимает только анализ 1.6 / анализатор 1.6.1 и необязательные
срезы 1.8 / расчётчик 1.8.0; другие версии требуют отдельной проверки
контракта, а не изменения allowlist.

Запись, связи, группы и CSV обрабатываются через SQLite курсорами и пакетами;
список всех ошибок в Python не создаётся. Прежние агрегаты и CALL остаются
в памяти: полного перевода всего анализатора на дисковую обработку здесь нет.

Синтетические проверки: [tests/test_error_detail.py](tests/test_error_detail.py).
Они покрывают повторные сообщения/обёртки, разные CALL/сеансы/потоки,
разные полные тексты при одинаковой сигнатуре, границы и полночь,
неоднозначность, пропуски, длинные тексты, исходные байты, пакет > 1000,
стабильность ID, подмену evidence/версии и загрузку старого комплекта.
