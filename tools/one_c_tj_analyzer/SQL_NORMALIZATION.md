# Контракт нормализации SQL 2.0

Нормализация 2.0 введена в схеме 1.4 и без изменений используется в текущей схеме 1.6. Последняя дополнительно сохраняет полные SQL и DB-события; расчётчик 1.8.0 принимает 1.2–1.6. Актуальный контракт хранилища и совместимости: [EVENT_DETAIL.md](EVENT_DETAIL.md).

Анализатор **1.4.0** записывает схему результатов **1.4**,
`sql_normalization_version: "2.0"`, `numeric_rules_version: "1.0"`.
Числовая семантика схемы 1.3 сохранена. Новая версия SQL самостоятельна:
она не является номером схемы результатов или правил связывания событий.

## Идентичность запросов

Вход — **полное значение атрибута Sql** после разбора записи ТЖ. Нормализация
выполняется до создания `sample_sql`; ограничение образца в 2400 символов
не применяется к `normalized_sql` и не влияет на fingerprint.

SQL разбирается на токены. Пробелы вне кавычек и комментарии удаляются,
между результирующими токенами вставляется один пробел. Неквотированные
слова приводятся к нижнему регистру. Содержимое кавычек идентификаторов,
включая пробелы, регистр и удвоенные кавычки, сохраняется.

Временные отношения получают номера `<temp:1>`, `<temp:2>`, … в порядке
первого обращения в полном SQL. Нумерация начинается заново для каждого
DBPOSTGRS. Повторные ссылки используют тот же номер, включая квалификаторы
полей перед FROM и коррелированные ссылки во вложенных SELECT.
Явные алиасы сохраняются и имеют приоритет над именами внешних таблиц.

| SQL | Канонические отношения |
|---|---|
| `FROM tt10 a JOIN tt20 b ON a.id=b.id` | `<temp:1> a JOIN <temp:2> b` |
| `FROM tt90 a JOIN tt80 b ON a.id=b.id` | те же два отношения |
| `FROM tt90 a JOIN tt90 b ON a.id=b.id` | `<temp:1> a JOIN <temp:1> b`, другая сигнатура |
| `FROM tt10 a JOIN tt20 b ON a.id=b.id JOIN tt10 c ON b.id=c.id` | `1, 2, 1`, отличается от `1, 2, 2` |

Область распознавания временных таблиц:

- отношения `pg_temp.<имя>` и `pg_temp_<номер>.<имя>`;
- неквалифицированные `tt<цифры>` по принятому соглашению 1С;
- имена, объявленные ранее в том же SQL через `CREATE TEMP/TEMPORARY TABLE`.

`pg_temp.tt12` и неквалифицированное `tt12` имеют одну идентичность.
Иные явно указанные схемы сохраняются: `public.tt12` — физическое имя.
Разные явные `pg_temp_<номер>` не считаются одним пространством имён;
их соответствие текущему `pg_temp` без подключения к БД неизвестно.
Реальные каталоги PostgreSQL не читаются. Если физическая таблица имеет
неквалифицированное имя `tt<цифры>`, для её однозначного сохранения нужна
явная схема: по одному тексту ТЖ отличить её от временной невозможно.

Имена CTE, алиасы, поля, физические таблицы и индексы не перенумеровываются.
Прежняя замена суффиксов любых `index_<номер>`/`tmpind_<номер>` удалена.
Обрабатываются FROM/JOIN, списки FROM через запятую, UPDATE, INSERT INTO,
DELETE USING, основные позиции таблиц в DDL и вложенные SELECT.
Это разбор позиций отношений, а не полный синтаксический анализатор PostgreSQL:
экзотические конструкции могут остаться несвёрнутыми. Bare whole-row ссылки
вида `SELECT tt12 FROM tt12` не переименовываются в списке SELECT: без каталога
они неоднозначны с одноимённым полем. Совпадение сигнатур не доказывает
эквивалентность планов, параметров или результатов выполнения.

## Литералы и структура

Обычные строки с удвоенными кавычками, `E'…'`, `U&'…'`, `N'…'` и dollar-quoted
строки с точным совпадением тега превращаются в `<string>`. SQL-подобное
содержимое литерала не разбирается как SQL. B/X литералы получают `<bits>`;
числа, включая десятичные дроби, экспоненты и префиксы систем счисления, —
`<number>`. Представление маркеров отличается от последовательности обычных
SQL-токенов и не подменяет параметр `$1` или оператор `?`.

Сохраняются операторы, знаки, скобки, поля, алиасы, приведения типов,
количество элементов IN, порядок JOIN и структура CASE/UNION/ORDER BY.
`x-1` отличается от `x+1`; `$1+$1` отличается от `$1+$2`.
Позиционные номера ORDER/GROUP BY и числовые модификаторы стандартных типов
(`numeric(10,2)`, `varchar(20)` и др.) сохраняются как структурные значения.

Однострочные `--` комментарии заканчиваются переводом строки, `/*…*/`
могут быть вложенными. Комментарий разделяет токены. Соседние строковые
константы с переводом строки объединяются по правилам PostgreSQL;
пробел без перевода строки не даёт такого объединения.

Лексические правила сверены с официальной
[документацией PostgreSQL](https://www.postgresql.org/docs/current/sql-syntax-lexical.html).
Нормализатор не выполняет SQL и не обращается к серверу.

## Неполный или неоднозначный SQL

Незакрытые строки/комментарии/скобки, неизвестные символы, конфликтующие
привязки отношений, Unicode-escaped идентификаторы `U&"…"` и обычные строки
с обратной косой чертой сохраняются в форме:

```text
<raw-sql> JSON_STRING_С_ПОЛНЫМ_ИСХОДНЫМ_SQL
```

Это `sql_normalization_status: "raw_fallback"`. Текст сохраняется без потерь,
включая пробелы, и получает fingerprint по тому же версионированному контракту.
Форма не смешивается с нормализованными запросами; её структурные флаги —
`null` в JSON и пустые ячейки CSV. При успешном разборе статус — `normalized`.
Для обычных строк с `\` такой выбор нужен потому, что значение серверного
`standard_conforming_strings` в сохранённой записи неизвестно. E-строки имеют
явную семантику экранирования и обрабатываются обычным способом.

## Формат и потребители

`analysis_metrics.json` получает обязательные поля:

```json
{
  "schema_version": "1.4",
  "sql_normalization_version": "2.0",
  "sql_fingerprint_algorithm": "sha256:1c-tj-sql-nul-version-nul-text:utf8"
}
```

В каждой строке `heavy_sql` JSON/CSV и каждом элементе
`operations[].top_nested_sql` обязательны `sql_normalization_version`,
`sql_normalization_status`, `normalized_sql`, `sql_fingerprint_sha256`.
Последние два поля уже существовали у heavy_sql; у вложенного SQL fingerprint
добавлен. Хеш вычисляется точно как:

```python
sha256(("1c-tj-sql\0" + sql_normalization_version + "\0" + normalized_sql).encode("utf-8")).hexdigest()
```

Логический ключ SQL: `(sql_normalization_version, sql_fingerprint_sha256)`;
для статистики замера к нему добавляется `measurement_id`. Даже при совпадении
канонического текста старый и новый алгоритмы дают разные fingerprints.
Внутри одного комплекта допустима ровно одна версия нормализации.

`slice_input.py` и `verify_analysis.py` проверяют версию, алгоритм, статусы,
хеш полного сохранённого normalized_sql и согласованность JSON/CSV.
Загрузчик также проверяет вложенный SQL. Отсутствующие версии в 1.4, неизвестные
версии, несовпадения строк, старый хеш в новой строке и новые поля в старой схеме
отклоняются.

Схемы 1.2/1.3 остаются читаемыми со строго выделенным профилем
`1.0-regex`: SHA-256 непосредственно от старого normalized_sql.
Пересчёт из старого sample_sql запрещён: он может быть обрезан.
Для получения 2.0 из старого комплекта нужен отдельный будущий запуск по
полным исходным SQL, а не переименование версии или повторное хеширование
старой нормализованной строки. Автоматической миграции нет.

Расчётчик **1.8.0**, схема срезов **1.8**, читает анализ 1.2–1.6 и сохраняет
`input_sql_normalization_version` в `slice_manifest.json`; `verify_slices.py`
проверяет это поле. Старые срезы требуют соответствующей версии проверяющего
кода. Универсальный PDF-визуализатор принимает только анализ 1.6 / анализатор
1.6.1 и необязательные срезы 1.8 / расчётчик 1.8.0. Расширение allowlist без
проверки контракта не является миграцией.

Изменены: `sql_normalization.py`, `analyze_1c_tj.py`, `slice_input.py`,
`slice_config.py`, `slice_metrics.py`, `slice_operations.py`, `derive_slices.py`,
`verify_analysis.py`, `verify_slices.py`, `audit_stage1.py`, инструкции и тесты.
Разбор хранит токены только обрабатываемого SQL; новый кэш всех исходных SQL
не создаётся. Хранение отдельных DB-событий и полных связей остаётся отдельным
этапом проекта схемы 2.0.

## Критерии проверки

`tests/test_sql_normalization.py` проверяет эквивалентные переименования,
квалификаторы, повторные обращения, self-JOIN, алиасы/CTE, физические имена,
вложенные запросы, DML/DDL, литералы, комментарии, операторы, параметры,
позиционные ссылки и модификаторы типов. Отрицательные пары обязаны иметь
разные нормализованные тексты и fingerprints.

Синтетический комплект DBPOSTGRS проверяет объединение двух переименований
и отделение self-JOIN, ссылку из CALL, JSON/CSV и полный цикл срезов.
Запросы с одинаковым sample_sql и различными полями после 2400-го символа
обязаны остаться разными. Повреждение версии, статуса, алгоритма, вложенного
SQL или хеша должно отклоняться. Старый профиль проверяется отдельно.
Реальные журналы для этих тестов не нужны.
