# Детерминированная история числовых проблем

Расчётчик 1.8.0; схема результата 1.8; конфигурация 1.0; входные схемы Анализатора ТЖ 1.2–1.6.

Это история срабатываний явно заданных числовых правил, а не перечень доказанных дефектов. Она сохраняет проблемы, впервые наблюдавшиеся в первом замере, и последовательно добавляет поздние срабатывания. Разные показатели и разные базы сравнения не сворачиваются в одну оценку.

## Запуск без чтения исходных журналов

Из каталога `tools/one_c_tj_analyzer`:

```powershell
python -B .\derive_slices.py --list-problem-metrics

python -B .\derive_slices.py `
  --analysis-dir "C:\Path\To\saved_analysis" `
  --config .\configs\problems.example.json `
  --output-dir "C:\Path\To\new_problem_history"

python -B .\verify_slices.py `
  --analysis-dir "C:\Path\To\saved_analysis" `
  --slices-dir "C:\Path\To\new_problem_history"
```

Можно выбрать часть таблиц через `--slices problem_registry problem_history problem_rule_coverage`. Источник — валидированный комплект сохранённых CSV/JSON, а не каталог ТЖ. Единственная популяция наблюдений — строки `call_observations.csv`. JSON и другие CSV используются для проверки согласованности и метаданных, но не добавляют дубли CALL. Расчётчик не читает пути исходных журналов/архивов из метаданных, не вызывает парсер, сеть, LLM и генератор PDF.

Для каждого запуска используйте новый выходной каталог. Существующий результат не перезаписывается без явного `--overwrite`; безопаснее сохранить обе версии. Подробные ограничения записи и проверка входной схемы описаны в [SLICES_RUNBOOK.md](SLICES_RUNBOOK.md).

## Правила и числовые основания

Пример блока конфигурации:

```json
{
  "problems": {
    "series_id": "my_stable_measurement_series",
    "rules": [
      {
        "rule_id": "call_p95_above_10s",
        "metric": "operation.p95_us",
        "operator": ">",
        "threshold": 10000000,
        "min_call_count": 10,
        "source": "Предлагаемый диагностический порог; не утверждённый SLA",
        "scope": "same_user",
        "signatures": null,
        "users": null,
        "require_clean_sources": false
      }
    ]
  }
}
```

Обязательны непустой `series_id` и хотя бы одно правило, если выбран любой проблемный срез. У правила обязательны `rule_id`, `metric`, `operator`, `threshold`, `min_call_count`, `source`. Идентификаторы правил уникальны. Неизвестные поля, метрики, подписи операций и пользователи в фильтрах вызывают ошибку, а не молчаливое игнорирование.

- `metric` — только из каталога `--list-problem-metrics`: существующие показатели `operation.*`, `db_chatty.*`, а также `apdex.deficit`, `apdex.frustrated_count`, `apdex.forced_frustrated_count`. Произвольные выражения и исполняемый код не допускаются.
- `operator` — `>` или `>=`. Рост выбранной величины считается неблагоприятным направлением **этого правила**, а не диагнозом системы. Для низкого APDEX используется величина `apdex.deficit = 1 − APDEX`.
- `threshold` — конечное неотрицательное число. Единицы доступны в каталоге метрик и колонке `metric_unit`; длительности `*_us` — микросекунды, объёмы — байты, проценты — шкала 0–100. Суффиксы `sum`, `mean`, `per_call`, `max` существенны: сумму нельзя интерпретировать как среднее на CALL.
- `min_call_count` — минимальное N группы для разрешения сравнения и классификации по правилу. N группы — не количество CALL, превысивших внутренний DB-порог.
- `source` — пояснение происхождения порога. Этот текст сохраняется, но не участвует в обнаружении проблем. Прежние тексты отчётов не используются.
- `scope` — только `same_user`: точная сигнатура и один пользователь. Разные пользователи, похожие подписи и разные показатели не объединяются. Неизвестная личность пользователя делает сравнение недостаточно определённым.
- `signatures`, `users` — `null` для всех или списки точных значений. Эвристического объединения и поиска по подстроке нет.
- Для любой метрики `db_chatty.*` обязателен `db_events_threshold`: внутренний порог K для отдельных CALL с `db_count > K`. Внешнее правило, например `calls_above_threshold_count > 0`, отдельно проверяет количество таких CALL. Среднее группы не заменяет проверку отдельных CALL.
- Для DB-метрик можно задать `min_db_linked_count_percent` и/или `min_db_linked_duration_percent`: `null` либо число 0–100. Это дополнительные фильтры достаточности по покрытию **всего замера**, не гарантия корректной связи конкретного CALL.
- `require_clean_sources=true` запрещает сравнение при зарегистрированных проблемах связанных источников или CALL из частичных файлов. Значение `false` сохраняет вычислимое сравнение вместе с предупреждениями; оно не означает, что источники полны.

В `configs/problems.example.json` предложены следующие диагностические правила. Они не являются согласованным SLA или официальными нормативами 1С.

| Правило | Числовой критерий | Минимальное N для оценки |
|---|---|---:|
| Длительный p95 CALL | p95 > 10 секунд | 10 |
| Максимальная задержка CALL | maximum > 30 секунд | 1 |
| Среднее DB/CALL | mean > 500 событий | 10 |
| Единичный высокоплотный CALL | maximum DB/CALL > 1000 | 1 |
| Наличие CALL с DB > 500 | количество таких CALL > 0 | 1 |
| Средний объём ответа | OutBytes/CALL > 10 MiB | 3 |
| Низкий APDEX при заданном T | 1 − APDEX > 0,15 | 10 |

Минимум N не скрывает первое зарегистрированное превышение. Оно создаёт карточку даже на недостаточной выборке: `threshold_breached=true`, но `threshold_status=недостаточно данных` и `first_problem_evaluable=false`. Это кандидат для повторного замера, не подтверждение повторяемости. Если первый проблемный замер не проходит фильтры достаточности, дельты относительно него не рассчитываются; последующие пригодные наблюдения всё равно можно сравнить между собой.

## APDEX

Для APDEX действуют существующие явные настройки T, их происхождения и политики подтверждённых неуспехов: [APDEX_RUNBOOK.md](APDEX_RUNBOOK.md). Конфигурация примера проблем намеренно не задаёт T. Без T правило отражается в `problem_rule_coverage.csv` как непроверенное (`APDEX_T_not_defined`); отсутствие карточек APDEX не означает приемлемый APDEX.

Дефицит вычисляется из целочисленных категорий как `(2N − 2S − U) / (2N)`, где S — удовлетворительные, U — допустимые наблюдения. Это избегает ложного превышения точного порога 0,15 при вычислении `1 − float(APDEX)`. Исходный APDEX сохранён в `source_metric_value`, а направление истории относится к **дефициту**. T, его статус, источник и политика ошибок также сохраняются. EXCP не превращается автоматически в неуспешную бизнес-операцию. Это APDEX серверных CALL, не end-to-end отклик.

## Идентичность и хронология

`problem_id` зависит от стабильного `series_id`, смыслового определения правила, точной сигнатуры и пользователя. `rule_definition_id` учитывает метрику, оператор, порог, минимальное N, фильтры качества и параметры расчёта: K, границу быстрого CALL для соответствующих метрик, T и политику APDEX. Изменение этих условий создаёт другую идентичность правила. Изменение только поясняющего `source` не создаёт новую проблему.

Новые измерения, хеш нового входного комплекта и дата первого обнаружения не входят в идентификатор проблемы. Поэтому добавление замеров сохраняет ID. Для той же серии сохраняйте `series_id`; для независимой серии задавайте другой. Идентификаторы первичных строк сохраняются отдельно для трассируемости и могут измениться при смене комплекта. Фильтры отбора не переименовывают существующие проблемы.

История каждый раз строится из **всей серии во входном комплекте**. Старый реестр не является вторым источником наблюдений и не подмешивается. Если передать комплект без старых замеров, отсутствующая история не восстанавливается предположениями. Для продолжения полной истории вход должен содержать все нужные замеры.

Используется хронология `OperationSeries` по сохранённым временным данным. Неоднозначный порядок требует явного `operations.measurement_order`; первое и последнее измерение не угадываются по имени каталога. Фильтр `measurement_ids` ограничивает строки истории и переходов, но не меняет первую проблемную базу, предыдущую базу и последний замер **полной** серии. Реестр и актуальные выборки всегда описывают последний замер полного комплекта; `latest_check_scope` явно сообщает это.

Первое превышение — первый замер, где число удовлетворяет правилу, а не дата появления проблемы в коде. В истории сохраняется строка для каждого последующего замера, включая отсутствие CALL. Промежуточное отсутствие не разрывает идентичность и не заменяется нулём.

## Статусы, сравнения и качество

Не существует единой колонки «вердикт». Состояние порога и оба направления динамики независимы:

| Колонка | Смысл |
|---|---|
| `threshold_status` | «порог превышен», «ниже порога в наблюдениях», «недостаточно данных» или «не наблюдалось» |
| `first_problem_change_status` | «показатель снизился» / «показатель вырос» относительно первого проблемного замера; иначе отсутствие/недостаточность данных |
| `previous_comparable_change_status` | Такое же направление относительно ближайшего предыдущего пригодного наблюдения той же пары операция–пользователь |

При точном равенстве показателей `change_status` пуст, а `change_direction=unchanged`; новый, не согласованный статус не выдумывается. Для строгого правила `>` значение, равное порогу, **не превышает** его: используется категория «ниже порога в наблюдениях» в смысле «правило не сработало», а `threshold_relation="="` сохраняет точное отношение. Для `>=` равенство является превышением по правилу.

Если CALL не наблюдались, N=0, `value` пусто, статус «не наблюдалось». Это не улучшение. Если наблюдение есть, но метрика отсутствует либо нарушены минимальное N/фильтры качества, статус «недостаточно данных», причины перечислены. `threshold_breached` отдельно сохраняет вычислимый числовой факт даже при недостаточности данных.

Дельты рассчитываются только при пригодности обеих сторон: абсолютная `current − reference`, процентная `100 × delta / reference`. При нулевой базе процент пуст, `percent_status=undefined_zero_reference`. Сохраняются ID, значения и N обеих сторон. Предыдущая пригодная база может находиться до первого превышения и может обходить пропущенный или недостаточный промежуточный замер; ID базы это показывает.

«Сопоставимое» здесь означает только точные сигнатуру/известного пользователя и выполненные числовые фильтры. Это **не контролируемый эксперимент**. Известные изменения N, процессов, наборов, качества и покрытия DB перечисляются; роль, документ, параметры, объём данных, версия кода, cold/warm и внешняя нагрузка могут быть неизвестны. Рост суммарного счётчика может отражать большее число CALL; снижение числа высокоплотных CALL может отражать изменение состава выборки. Не трактуйте это автоматически как ускорение алгоритма.

В реестре разделены `last_observed_measurement_id` (есть CALL), `last_value_measurement_id` (есть метрика), `last_evaluable_measurement_id` (пригодная оценка начиная с первого превышения), `observed_in_latest_measurement` и `checked_in_latest_measurement`. Последний пригодный замер не подставляется вместо отсутствующего последнего замера серии.

Ограничения источников наследуются из существующих срезов. В старой схеме отсутствующий счётчик мог быть сохранён нулём — это не восстанавливается. Нулевой DB/CALL не доказывает отсутствия обращений. Покрытие DB → CALL известно не с точностью до конкретной операции; значения не «исправляются» делением на процент покрытия. CPU, вложенные DB и CALL не становятся независимыми слагаемыми wall time. Ни DB-chatty, ни числовое изменение не доказывают N+1, исправление кода или причину задержки.

## Выходные таблицы и пять выборок

| Файл | Единица строки и отбор |
|---|---|
| `problem_registry.csv` | Одна карточка «правило × точная операция × пользователь». Упорядочена по первому превышению. Содержит его основание и состояние в последнем замере всей серии. |
| `problem_history.csv` | Карточка × замер от первого превышения до конца серии, включая отсутствие. Значения, N, порог, две базы сравнения, дельты и ограничения. |
| `problem_improved.csv` | Отдельное числовое снижение по одной базе (`comparison_basis`): первый проблемный либо предыдущий пригодный замер. Вся выбранная история, **не только последний замер**. |
| `problem_persisting.csv` | Карточки с пригодной оценкой и превышением правила в последнем замере полной серии. Недостаточная выборка сюда не маскируется как подтверждённое состояние. |
| `problem_worsened.csv` | Отдельное числовое увеличение по одной базе; вся выбранная история. Это не «регрессия кода». |
| `problem_new.csv` | По одной строке первого превышения. `discovery_phase=first_measurement` сохраняет исходный список; `later_measurement` добавляет впервые наблюдавшиеся позднее проблемы. |
| `problem_unchecked.csv` | Исторические карточки, появившиеся до последнего замера и не получившие в нём пригодной проверки: отсутствие, малое N, неизвестный пользователь или ограничения качества. |
| `problem_rule_coverage.csv` | Правило × замер: количество пар операция–пользователь, наблюдаемых/доступных/пригодных/превысивших порог; CALL и причины непроверенности. Включает правила без единого обнаруженного превышения. |
| `data_quality.csv` | Независимый срез качества входных данных по замерам. |
| `slice_manifest.json` | Версии, каноническая конфигурация, методика, хеши входов/выходов, число строк, результат проверки сохранности входов. |

Выборки **не складываются** в число дефектов. Одна карточка может дать много переходов; два правила могут сработать на одних CALL. Один переход может быть ниже первой проблемной базы, но выше предыдущей — обе записи сохраняются в разных выборках. CALL может ускориться, а DB/CALL вырасти — это разные карточки, без общего ярлыка. Для текущих переходов фильтруйте `is_latest_series_measurement=true`; для впервые наблюдавшихся в последнем замере — так же в `problem_new.csv`.

«Ниже порога в наблюдениях» не означает «исправлено». Отсутствие повторного наблюдения не означает «проблема исчезла». Новое срабатывание не означает «проблема появилась в этом релизе».

## Воспроизводимость и тесты

```powershell
python -B -m unittest discover -s .\tests
```

Тесты проблемного слоя проверяют сохранение первой проблемы и поздние дополнения; пропуски; разные пользователи и похожие сигнатуры; малые выборки; нулевую базу; равенство порогу; противоположные направления метрик и баз сравнения; индивидуальный DB-chatty при низком среднем; недоступный APDEX и его точные границы; фильтры качества; неопределённую хронологию; стабильные ID при добавлении замера; конфигурацию и порядок входных строк; отсутствие чтения исходных ТЖ/сети; отказ в неявной перезаписи; побайтовое совпадение двух запусков и сохранность входа.

Проверка `verify_slices.py` повторно вычисляет выбранные таблицы из сохранённых CSV/JSON и сравнивает байты, порядок строк, схему, метаданные и контрольные суммы. Она не подтверждает полноту первоначального ТЖ, корректность бизнес-расчётов или причинность выявленной динамики.
