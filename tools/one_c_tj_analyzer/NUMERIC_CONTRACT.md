# Качество числовых счётчиков: схема 1.3

Числовой контракт введён анализатором 1.3.0: `schema_version: "1.3"`,
`numeric_rules_version: "1.0"`. Анализатор 1.6.1 сохраняет эти правила в схеме 1.6;
изменение SQL описано отдельно в [SQL_NORMALIZATION.md](SQL_NORMALIZATION.md).
Расчётчик 1.8.0 читает схемы 1.2, 1.3, 1.4, 1.5 и 1.6, записывает срезы версии 1.8.
Числовая семантика первоначально введена в JSON/CSV. Реализация SQLite,
устойчивых ID и полного DB-экспорта в последующей схеме 1.5 описана в
[EVENT_DETAIL.md](EVENT_DETAIL.md); она сохраняет эти числовые правила.

## Наблюдения

| Атрибут ТЖ | Поле CALL | Единица | Допустимый диапазон |
|---|---|---|---|
| CpuTime | cpu_us | микросекунды | 0 .. 2^63−1 |
| Memory | memory | байты по записи ТЖ | −2^63 .. 2^63−1 |
| MemoryPeak | memory_peak | байты по записи ТЖ | −2^63 .. 2^63−1 |
| InBytes | in_bytes | байты | 0 .. 2^63−1 |
| OutBytes | out_bytes | байты | 0 .. 2^63−1 |
| RowsAffected | rows_affected | строки | 0 .. 2^63−1 |

Знак полей памяти сохранён согласно прежнему контракту загрузчика. Он не является
утверждением о физическом смысле отрицательной памяти. Duration и вычисленные
количества событий этим контрактом не изменяются.

В `call_observations.csv` и `top_calls.csv` добавлены `rows_affected`,
`numeric_quality`, `db_rows_quality`. `numeric_quality` — JSON-объект с шестью ключами
из таблицы. Каждый содержит `state`, `raw_value`, `value`, `unit`, `reason`.
`raw_value` — декодированное значение после существующего разбора атрибутов ТЖ,
не точная байтовая лексема исходного файла.

| Состояние | Значение | Пример |
|---|---|---|
| valid | точное целое, включая 0 | `CpuTime=0`, `CpuTime=20` |
| missing | null | атрибут отсутствует |
| empty | null | пустое или состоящее из пробелов значение |
| invalid | null | `abc`, `1.2`, `NaN`, `Infinity`, `1_000` |
| out_of_range | null | выход за диапазон соответствующего поля |

Для invalid/out_of_range сохраняется причина. В JSON неизвестное число — `null`,
в числовой CSV-ячейке — пустая строка. Корректный ноль записывается как `0`.
При чтении проверяются согласованность состояния, исходного значения и числового поля.

## Агрегаты и знаменатели

Каждый агрегат качества содержит:

- `eligible_count`: число наблюдений в обозначенной популяции;
- `available_count`: число наблюдений со state=valid;
- `missing_count`, `empty_count`, `invalid_count`, `out_of_range_count`;
- `zero_count`: число корректных нулей, входящих в available_count;
- `sum_known`: сумма доступных значений; null при available_count=0;
- `sum_complete`: та же сумма только при непустой полностью доступной популяции;
- `mean`: sum_known / available_count;
- `mean_denominator`: available_count, включая нулевые наблюдения;
- `max_known`: максимум доступных значений, null при их отсутствии;
- `coverage_percent`: 100 × available_count / eligible_count, null для пустой популяции.

Сумма available_count и четырёх количеств недоступных состояний равна eligible_count.
Суммы вычисляются целочисленно без ограничения разрядности Python; преобразования
индивидуального счётчика или суммы через float нет. Средние и проценты — дробные показатели.

Пример `[0, 20, missing, invalid]`: available_count=2, eligible_count=4,
sum_known=20, sum_complete=null, mean=10, mean_denominator=2, coverage_percent=50.
Для полностью неизвестной или пустой популяции сумма/среднее/максимум — null.

В `operations` поля `cpu_us`, `memory`, `in_bytes`, `out_bytes` теперь означают
сумму доступных значений. `*_per_call` делятся на число CALL с доступным
соответствующим счётчиком, а не на все CALL. MemoryPeak average/median/p95/max
считаются только по доступным значениям. Полный набор качества хранится рядом в
`numeric_quality`; он также присутствует в истории операций и её сводке всех пользователей.

## Три популяции RowsAffected

1. `CALL.rows_affected` — собственный атрибут CALL. В агрегате операций его сумма
   называется `call_rows_affected`, качество — `numeric_quality.rows_affected`.
2. `CALL.db_rows` — сумма доступных RowsAffected назначенных этому CALL DBPOSTGRS.
   Качество — `db_rows_quality`, eligible_count равен db_count. При отсутствии
   DB-событий или доступных RowsAffected значение null; число событий по-прежнему 0
   либо фактически зарегистрированное количество.
3. `operations.rows_affected` сохраняет прежнее происхождение из связанных DB,
   но суммирует только доступные значения. Качество — `numeric_quality.db_rows`;
   знаменатель среднего внутри этого объекта — доступные DB-события, не CALL.

В `heavy_sql` сохранены сумма и максимум доступных RowsAffected; добавлены
`rows_affected_per_event` и `numeric_quality` по всем шести полям. Знаменатель
rows_affected_per_event — только DB-события данного SQL-шаблона с доступным RowsAffected.
Статистика событий dataset.event_stats также содержит качество шести полей,
включая DBPOSTGRS без SQL и без связанного CALL. Отсутствующие атрибуты в этой
популяции считаются missing; наличие атрибута не предполагается обязательным
для каждого типа события. Отдельные DB-наблюдения пока не экспортируются.

## CPU% и согласованная выборка

Пусть C — CALL группы, у которых CpuTime имеет state=valid, включая CpuTime=0.

```text
cpu_percent_of_wall = 100 × sum(C.CpuTime) / sum(C.duration_us)
cpu_available_count = count(C)
cpu_wall_us = sum(C.duration_us)
cpu_coverage_percent = 100 × count(C) / count(all_CALLs)
cpu_wall_coverage_percent = 100 × sum(C.duration_us) / sum(all_CALLs.duration_us)
```

CPU% при нулевом знаменателе — null. CpuTime=0 при положительном времени даёт
корректный CPU%=0. Число доступных CPU и покрытие по числу/времени публикуются
в operations, identical_operations и истории срезов. Доли покрытия также входят
в таблицу сравнений срезов. Пропуски отдельных счётчиков доступны по каждой операции
в numeric_quality, по замеру — в data_quality.metric_availability.

`unattributed_us_floor`, `unattributed_percent_floor`, `attribution_overflow_us`
используют только C: его CALL duration, CPU и связанные DB duration. Без C эти
показатели null. Они относятся к покрытой части группы и не оценивают остаток
непокрытых CALL. Счётчики и интервалы остаются неаддитивными: ни CPU%, ни остаток
не являются установленной причиной задержки. Формулы агрегатного остатка и
overflow сохранены; изменена их популяция.

## Совместимость и проверки

Изменение семантики намеренно не помечено схемой 1.2. Её старые нули нельзя
ретроспективно разделить на missing/invalid/valid. При чтении 1.2 прежние
ограничения сохраняются, numeric_quality и новые CPU-показатели покрытия неизвестны.
Текущие результаты получают 1.6. Поддержка 1.3/1.4/1.5/1.6 не означает реализации схемы 2.0.

`verify_analysis.py` и загрузчик срезов проверяют состояния, суммы, средние,
покрытие и согласованный знаменатель CPU. Неизвестные схемы отклоняются.
`verify_slices.py` пересчитывает результат, `audit_stage1.py` 1.1.0 независимо
проверяет числовые показатели срезов. Потребители срезов должны принимать их
новую схему 1.8 и nullable-числа.

Универсальный PDF-визуализатор принимает только анализ 1.6 / анализатор 1.6.1
и необязательные срезы 1.8 / расчётчик 1.8.0. Остальные версии отклоняются;
добавление номера версии в allowlist без проверки контракта не является миграцией.

Тесты: `tests/test_numeric_quality.py` проверяет все шесть счётчиков, пустые и
смешанные популяции, нули, знаки и диапазоны, точность больших целых, CPU-популяцию,
RowsAffected, JSON/CSV, отклонение искажённых агрегатов и расчёт всех 26 срезов.
Используются только небольшие синтетические журналы и временные комплекты результатов.
