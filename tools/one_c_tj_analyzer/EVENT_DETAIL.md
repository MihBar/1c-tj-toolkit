# Полная детализация CALL → DBPOSTGRS → SQL

Анализатор **1.6.1**, схема комплекта **1.6**, схема SQLite **1.1**.
DB-детализация введена в 1.5; в 1.6 к ней добавлены [ошибки и гипотезы инцидентов](ERROR_DETAIL.md).
Нормализация SQL остаётся **2.0**, числовые правила — **1.0**.
Выбор владельца DB зафиксирован как **legacy_end_longest/v1**.

Это реализация таблиц событий, SQL и решений из проекта схемы 2.0.
Существующие JSON/CSV-сводки сохранены. Полная схема 2.0 не объявляется:
иерархия CALL и перевод всех старых
агрегаторов и потребителей на дисковый расчёт остаются отдельными этапами.

## Комплект и первичная популяция

К прежним 11 файлам добавлены пять обязательных артефактов:

| Файл | Содержание |
|---|---|
| `analysis.sqlite` | События, источники, полные SQL, числовые поля, решения и все кандидаты |
| `source_map.json` | Переносимая карта физических мест и логических источников |
| `db_observations.csv` | Каждое DBPOSTGRS, включая несвязанные и записи без SQL |
| `event_links.csv` | Ровно одно решение о CALL для каждого DBPOSTGRS |
| `link_candidates.csv` | Все CALL, содержащие DB.end в прежней области поиска; без top-N |

CSV — UTF-8 с BOM, `NULL` — пустая ячейка. Словарь полных SQL находится
в SQLite; в DB-экспорте есть ссылки и fingerprint, а текста Sql нет.
Содержимое `Context` не обрезается. Числовая колонка сопровождается
`numeric_quality` с исходным значением, состоянием, единицей и причиной.

`operations[].top_nested_sql` сохраняется как **предварительный список до
10 шаблонов** для прежних потребителей. Это не полная связь и не источник
итоговых сумм. Полный набор доступен по `call_event_id` в `db_observations`
и не ограничен числом шаблонов, событий или выбранных top_calls.

`analysis_metrics.json` сохраняет версии из `event_store.VERSIONS`, машинное
описание `linkage_rules`, `event_detail_scope=["CALL","DBPOSTGRS","EXCP","QERR"]`,
`publication_state`, `source_processing_complete`, `capture_id`,
`capture_identity_status`, `collection_completeness="unknown"` и `artifacts`.
Для каждого нового артефакта указаны SHA-256, размер и число строк.
Для SQLite число строк — количество записей `events`.

## Таблицы SQLite

Точные имена, типы, ключи и ограничения определены в [event_schema.sql](event_schema.sql).

| Таблица | Ключ и назначение |
|---|---|
| `source_streams` | `source_id`; сбор, origin, область процесса, логический журнал, качество идентификации |
| `source_versions` | `source_version_id`; источник, SHA-256 всего несжатого потока, размер, обработанные байты и статус |
| `source_locations` | `location_id`; версия источника, путь, тип контейнера, имя и порядковый номер элемента |
| `events` | `event_id`; исходные координаты/хеш, тип/уровень, время/длительность, dataset/measurement, пользователь, процесс, поток, сеанс, connectID, Dbpid, полный Context и прочие атрибуты |
| `call_events` | `event_id → events`; прежний последовательный `legacy_call_id`, сигнатура и её версия |
| `db_events` | `event_id → events`; nullable `sql_text_id`, состояние наличия SQL |
| `sql_texts` | `sql_text_id`; полный декодированный Sql и его SHA-256, одна строка на точный текст |
| `sql_patterns` | `pattern_id`; версия, полный normalized_sql, fingerprint и статус нормализации |
| `sql_normalizations` | `(sql_text_id, normalization_version)`; ссылка на шаблон и состояние |
| `numeric_values` | `(event_id, field_name)`; все шесть счётчиков и их качество |
| `link_decisions` | `event_id → db_events`; версия, выбранный parent, статус, причина и количества кандидатов |
| `link_candidates` | `(event_id, call_event_id)`; проверки сеанса/соединения/интервала, допуск и выбор |
| `parse_issues` | Исходный диапазон и причина пропуска/повреждения |

Представление `db_observations` соединяет событие с SQL-шаблоном, решением
и CALL. SQL-текст можно получить отдельно через `sql_texts` по `sql_text_id`.
Первичная таблица DB не содержит нормализованный или исходный текст.
Sql также исключён из `events.attributes_json`, чтобы избежать дублирования.
Несколько разных буквальных SQL могут ссылаться на один шаблон.

`sql_presence_state`: `missing` — атрибута нет; `empty` — декодированная строка
пуста; `present` — строка непуста. Только `present` имеет SQL-ссылку.
Наличие строки не является проверкой исполнимости SQL. `raw_fallback` хранится
по прежнему контракту [SQL_NORMALIZATION.md](SQL_NORMALIZATION.md).

Другие распознанные типы тоже записываются в общую `events`, но полный
контракт решений/экспортов этого этапа относится к CALL и DBPOSTGRS.
Связи SDBL/блокировок/ошибок по-прежнему представлены прежними агрегатами.

## Устойчивые ID и источник

`H` — SHA-256 от UTF-8 канонического JSON-массива аргументов
(`ensure_ascii=False`, `sort_keys=True`, разделители `,` и `:`).

```text
source_id = H("source/v1", capture_id, origin_id, process_scope, logical_log_key)
source_version_id = H("source-version/v1", source_id, SHA256(несжатый поток))
event_id = H("event/v1", source_id, byte_start, raw_record_sha256)
sql_text_id = H("sql-text/v1", полный декодированный Sql)
pattern_id = H("sql-pattern/v1", normalization_version, sql_fingerprint_sha256)
```

Версии нормализации/связывания, sequential call_id, абсолютный путь и версия
дописанного файла не входят в event_id. Добавление другого файла или
дописывание журнала не меняет ID записей с неизменными байтами и границами.
В `call_observations.csv`/`top_calls.csv` добавлены `event_id`, `source_id`,
`source_version_id`, позиции, хеш записи, `thread`, `session`, `connect_id`.
Поле `call_id` сохранено как локальный номер старых сводок; для устойчивых
внешних ссылок используется `event_id`.

Координаты считаются в **несжатых байтах до декодирования**:
`[byte_start,byte_end)`, с нуля; `record_ordinal`, `line_start`, `line_end` —
с единицы. В хеш входят точные исходные байты записи, включая завершающие
CR/LF и BOM первой записи. Для ZIP/TAR номер элемента начинается с нуля
и учитывает все элементы контейнера, включая каталоги. Одинаковые имена
элементов не означают одну запись. Для GZIP позиции и размер относятся
к распакованному потоку. Абсолютные пути сохраняются только как происхождение.

Схема 1.5 всегда хеширует полный несжатый источник; прежний `--hash-sources`
допускается как совместимый параметр. При NUL хеш полного потока отделён
от количества обработанных байтов, исключённый диапазон записан в parse_issues.
При ошибке чтения статус частичный; хеш не объявляется полным, если его
невозможно было получить при предварительной проверке.

Для нового сбора рекомендуется задавать постоянный `--capture-id`.
Без него ID сбора детерминированно выводится из исходного корня и получает
`capture_identity_status=inferred_root`. Для переноса такого сбора обязательно
повторно использовать экспортированный `source_map.json`; иначе корень
будет считаться другим сбором. Сам по себе одинаковый SHA-256 не доказывает
общность логического источника.

Минимальный элемент карты:

```json
{
  "source_identity_version": "1.0",
  "capture_id": "capture-2026-09-03",
  "sources": [{
    "locator": {
      "path": "capture/rphost_1/26090310.log",
      "kind": "loose",
      "member": "",
      "member_ordinal": null
    },
    "origin_id": "server-A",
    "process_scope": "rphost_1",
    "logical_log_key": "rphost_1/26090310.log"
  }]
}
```

У архивной и распакованной копий задаются разные `locator` и одинаковая
логическая тройка origin/process/logical_log_key. При совпадении полного
хеша они учитываются один раз; все физические места остаются в БД.
Конфликтующие версии одного логического источника отклоняются до публикации.
Новые файлы, не перечисленные в карте, получают идентичность из относительного
пути и явную пометку `inferred_relative_path`.

Это отдельно версионированное изменение дедупликации: прежний режим
`--hash-sources` объединял одинаковые байты даже из независимых источников.
Теперь объединение требует совпадения **логической идентичности и хеша**.
Для файлов без карты прежняя ложная дедупликация может исчезнуть, увеличив
число учтённых наблюдений. Режим `--archive-mode auto` по-прежнему исключает
архив при наличии распакованного соседа; для чтения обоих нужен `always` и карта.

## Неизменённый выбор CALL и явная неопределённость

Правило `legacy_end_longest/v1` дословно сохраняет прежнюю методику:

1. Область поиска: одинаковые `dataset_id`, нормализованный пользователь,
   процесс и OSThread. При отсутствии времени DB или потока связи нет.
2. Кандидат содержит **время окончания** DB, обе границы включены.
   Полное вхождение DB-интервала записывается только как диагностический флаг.
3. При непустом DB.SessionID и наличии совпадений остаются CALL с этим сеансом.
   Если совпадений нет либо SessionID отсутствует, остаются все кандидаты.
4. Выбирается максимальная duration_us; при равенстве — минимальный прежний
   call_id. ConnectID не исключает кандидатов. Разделение measurement по
   календарным дням не запрещает связь через полночь.

Вложенный DB назначается внешнему, самому длинному CALL. Новый предложенный
алгоритм с полным интервалом и внутренним владельцем **не включён**.
Исправлена адресация одноимённых элементов архивов (`parser_version=2.0`);
раньше чтение по одному имени могло дважды прочитать другой элемент. Это
может изменить исходную популяцию такого архива, а не критерий выбора CALL.

| Статус | Смысл |
|---|---|
| `linked_unique` | После приоритета сеанса один кандидат, обязательные признаки доступны |
| `linked_by_rule` | Один кандидат выбран с резервным допущением: SessionID отсутствует/не совпал либо отсутствует пользователь |
| `ambiguous` | После фильтра несколько кандидатов; выбранный старым правилом parent всё равно сохранён |
| `unlinked` | Время/поток отсутствуют или содержащего CALL нет; parent равен NULL |

`candidate_count` — все содержащие DB.end CALL в прежней области поиска;
`session_match_count` — совпадения с непустым SessionID DB;
`eligible_count` — кандидаты после приоритета сеанса. `fallback_applied`
публикуется отдельно, в том числе при `ambiguous`.
Конфликт сеансов, отсутствующие ключи и совпадение/конфликт connectID
сохранены в evidence. CALL из других потоков/процессов/пользователей
не входят в область кандидатов; это не список всех CALL всего сбора.

## Учёт, проверка и ограничения

На DB есть одна строка db_events, одно решение и не более одного выбранного
кандидата. Это закреплено PK/FK и уникальным частичным индексом.
Суммы CALL и операций берутся один раз из выбранного владельца. Предки
CALL не получают дополнительных копий DB. Все кандидаты, SQL-тексты и
SQL-шаблоны являются справочными сущностями, а не наблюдениями.

Проверяются равенства: все DB = связанные + несвязанные; назначенные
DB каждого CALL = его db_count/db_duration_us/качество RowsAffected;
SQL-группы = DB с непустым Sql. Нельзя складывать общий список DB,
SQL-группы и link_candidates как независимые нагрузки.
Длительности каждого DB сохранены отдельно для будущих точных перцентилей.

Первичная запись и CSV-выгрузки потоковые: SQLite-пакеты по 1000 событий,
дисковые временные структуры и кеш 8 МиБ. Словарь полных SQL и кандидаты
не накапливаются в Python-списках. **Общего ограничения памяти всего анализа
это ещё не даёт**: прежние CALL, агрегаты, списки длительностей и потребители
сводок остаются в памяти. Для полного профиля памяти из проекта 2.0 требуется
следующий переход агрегаторов на дисковые выборки.

Комплект сначала строится в отдельном временном каталоге. После закрытия БД
проверяются целостность/FK, версии, координаты/ID, все числовые состояния,
полные SQL и fingerprints, каждое решение и все кандидаты, суммы и CSV-зеркала.
Манифест переносится в результат последним. Ошибка до публикации сохраняет
предыдущий комплект; незавершённая замена обнаруживается по контрольным суммам.

Расчётчик **1.8.0**, схема срезов **1.8**, читает анализ 1.2–1.6.
Для 1.5 идентичность входа включает 16 файлов, для 1.6 — 21 файл; версия связывания
передаётся в `input_linkage_rules_version`. Проверки и срезы не открывают
исходные журналы и пути происхождения. Универсальный PDF-визуализатор принимает
только анализ 1.6 / анализатор 1.6.1 и необязательные срезы 1.8 / расчётчик
1.8.0; другие версии требуют отдельной проверки контракта, а не изменения
allowlist.

Тесты в [tests/test_event_detail.py](tests/test_event_detail.py) используют
только синтетические ТЖ: более 10 шаблонов, повторный SQL, отсутствие SQL,
вложенные/пересекающиеся CALL, равные длительности, разные/отсутствующие
сеансы, потоки и пользователи, обе границы CALL, DB.start вне CALL,
переход суток, Unicode/BOM/CRLF/CR, GZIP, повторяющиеся имена архивных элементов,
перенос/дописывание, логические копии, границу пакета, повреждение evidence,
работу без исходников и сохранность предыдущего результата при ошибке.
