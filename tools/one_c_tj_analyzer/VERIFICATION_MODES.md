# Полная и базовая проверка

`analyze_1c_tj.py` и `derive_slices.py` принимают `--verification full|basic`.
Без параметра остаётся `full`. Неверное значение отклоняется до чтения ТЖ.

`basic` сохраняет загрузку и типизацию CALL, неизвестные значения, обязательные
файлы и схемы, уникальность ключей, ссылки CALL на источники, безопасные пути,
хеши артефактов и неизменность комплекта. Он не выполняет полную сверку CSV/JSON,
пересчёт агрегатов, сверку SQLite с CSV, проверку всех событий и кандидатов,
`integrity_check` и `foreign_key_check`. Хеширование всё ещё читает файлы целиком.
Ошибки чтения, структуры и расчёта не подавляются. Пропуск проверки не исправляет
ошибки данных и не гарантирует сокращения времени самого разбора или расчёта.

```powershell
python -B tools/one_c_tj_analyzer/analyze_1c_tj.py C:\Logs --output-dir C:\Results\analysis --verification basic --progress
python -B tools/one_c_tj_analyzer/derive_slices.py --analysis-dir C:\Results\analysis --config tools/one_c_tj_analyzer/configs/slices.example.json --output-dir C:\Results\slices --verification basic
```

Параметр нужно передавать **обоим** этапам. Режим из сохранённого комплекта
автоматически не наследуется: обычная загрузка и самостоятельные верификаторы
по-прежнему выполняют полную проверку.

## BAT

Скопируйте `scripts/settings.example.bat`, задайте `TJ_LOG_DIR`, `TJ_SLICE_CONFIG`,
при необходимости `TJ_PYTHON` и `TJ_OUTPUT_ROOT`. Установите `TJ_VERIFICATION=basic`.
Запустите `scripts\run_analysis.bat путь\к\settings.bat`; для проверки настройки
добавьте вторым аргументом `--check`. При `basic` отдельные этапы верификации
анализа и срезов пропускаются. Каждый запуск создаёт отдельный каталог.
Выбор срезов, включая исключение APDEX, остаётся в конфигурации срезов.

## Метаданные и идентичность

В `analysis_metrics.json` и `slice_manifest.json` добавлено необязательное поле
`verification` с версией политики `1`, режимом, областью `saved_analysis_bundle`,
статусом глубокой проверки этой области и выполненными/пропущенными группами.
Поле записывается после успешной загрузки/проверки. В манифесте срезов оно описывает
проверку **входного анализа**, а не независимый повторный расчёт выходных срезов.
`validation_checks` содержит только фактически выполненные проверки.
Старые комплекты без нового поля поддерживаются.

`analysis_complete`, `source_processing_complete` и `publication_state` сохраняют
свой прежний смысл. Они не означают успешную полную верификацию.
В `basic` итог срезов имеет статус `OK` и сообщение «Полная верификация не выполнялась».
PDF отображает сохранённый статус; собственная структурная проверка PDF остаётся
включённой и не является независимой проверкой аналитики.

Для **одного сохранённого комплекта** оба режима дают одинаковый `bundle_id`:
состав файлов и алгоритм хеширования не меняются. Разные запуски `full` и `basic`
имеют разные метаданные анализа и поэтому могут иметь разные `bundle_id`, хотя
аналитические значения совпадают. Новое поле также меняет идентификатор по сравнению
с результатом старой версии. Правила анализа, идентификаторы событий и CALL не меняются.

## Проверка позже

```powershell
python -B tools/one_c_tj_analyzer/verify_analysis.py --analysis-dir C:\Results\analysis
python -B tools/one_c_tj_analyzer/verify_slices.py --analysis-dir C:\Results\analysis --slices-dir C:\Results\slices
```

Обе команды выполняют полную проверку независимо от записанного режима. Для текущей
схемы 1.6 исходные ТЖ не перечитываются. Сохранённые данные и их идентификаторы
не переписываются: результат последующей проверки выводится отдельно. Поэтому
первоначальный статус подготовки в манифесте/PDF остаётся прежним.

Для сравнения времени используйте `--progress --progress-format jsonl` у анализатора:
фазы разбора, связывания, экспорта и проверки отмечены отдельно. Замер полного
запуска на синтетических данных проверяет работоспособность, но не даёт оценки
ускорения на большом пользовательском журнале.
