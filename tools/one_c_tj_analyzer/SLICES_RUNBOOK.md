## Реализованные срезы

Реализованы загрузка, валидация, контроль происхождения и неизменности данных, выбор срезов, безопасный экспорт, повторная проверка и двадцать шесть выбираемых таблиц:

- `data_quality` — качество и ограничения по замерам;
- `operation_history` — полная сетка «точная сигнатура × наблюдавшийся пользователь × замер»;
- `operation_history_all_users` — отдельная сводка по точным сигнатурам для всех пользователей;
- `measurement_comparisons` — четыре базы сравнения для одинаковых сигнатур и пользователей;
- `comparability` — признаки сопоставимости для каждой строки сравнения.

Независимый блок DB-chatty:

- `db_chatty` — средние групп и фактические превышения на CALL, по операции/пользователю/замеру/порогу;
- `db_chatty_calls` — отдельные CALL, превысившие хотя бы один настроенный порог;
- `db_chatty_fast_calls` — отдельная таблица быстрых CALL с превышениями;
- `db_chatty_duration` — распределение фактических превышений по диапазонам длительности;
- `db_chatty_coverage` — раздельный охват CALL, точных сигнатур операций и известных идентификаторов пользователей;
- `db_chatty_changes` — динамика относительно первого и предыдущего наблюдения той же операции у того же пользователя.

Независимый блок APDEX: `apdex`, `apdex_calls`, `apdex_uncovered`, `apdex_coverage`, `apdex_overall`, `apdex_composition`, `apdex_changes`. Это APDEX по зарегистрированным серверным CALL, не end-to-end. Без T показатели не рассчитываются; общий APDEX разделён по статусу целей и всегда экспортируется с составом выборки. Подробности: [APDEX_RUNBOOK.md](APDEX_RUNBOOK.md), конфигурация — `configs/apdex.example.json`.

История проблем: `problem_registry`, `problem_history`, `problem_improved`, `problem_persisting`, `problem_worsened`, `problem_new`, `problem_unchecked`, `problem_rule_coverage`. Основа — явные числовые правила для уже реализованных CALL-срезов; тексты отчётов не используются. Инструкция: [PROBLEMS_RUNBOOK.md](PROBLEMS_RUNBOOK.md), конфигурация — `configs/problems.example.json`. Запрос неизвестного среза завершается ошибкой.

Версия расчётчика — 1.8.0, выходной схемы — 1.8. Поддерживаются входные схемы 1.2, 1.3, 1.4, 1.5 и 1.6, конфигурация — 1.0 с дополнительными необязательными блоками `operations`, `db_chatty`, `apdex` и `problems`. Ранее созданные результаты не мигрируются и не перезаписываются. Верификатор требует соответствия версии расчётчика и схемы; для старого результата нужна соответствующая версия кода.

## Вход

Поддерживаются схемы `1.2`, `1.3`, `1.4`, `1.5` и `1.6`. Контракт nullable-счётчиков, доступности и знаменателей: [NUMERIC_CONTRACT.md](NUMERIC_CONTRACT.md). Отсутствующая, более старая или неизвестная будущая схема отклоняется; автоматической миграции нет. Версия исходного анализатора сохраняется отдельно от версии расчётчика. Версия нормализации SQL проверяется при загрузке и записывается в `input_sql_normalization_version` манифеста срезов; правила совместимости: [SQL_NORMALIZATION.md](SQL_NORMALIZATION.md).

В явно указанном каталоге должны лежать:

- `analysis_metrics.json`;
- `call_observations.csv`, `top_calls.csv`;
- `files.csv`, `datasets.csv`, `linkage.csv`;
- `operations.csv`, `identical_operations.csv`;
- `heavy_sql.csv`, `errors.csv`, `locks.csv`.

Подкаталоги не сканируются. Дополнительные файлы не читаются. Ссылки, выводящие обязательный файл за пределы выбранного каталога, отклоняются. CSV читается в UTF-8/UTF-8 BOM с запятой и поддержкой многострочных полей; ограничение размера одного поля — 16 MiB. Исходные скалярные значения не исправляются.

Единственная популяция CALL — строки `call_observations.csv`. Ключ — `(bundle_id, call_id)`. Идентификаторы должны быть положительными и уникальными; непрерывность нумерации не требуется. JSON-агрегаты и `top_calls.csv` служат проверками и не увеличивают N.

## Конфигурация

Пример только для качества: `configs/slices.example.json`. История операций и сравнения: **`configs/operations.example.json`**. Независимый блок DB-chatty и качество: **`configs/db_chatty.example.json`**. Можно комбинировать любые таблицы через список `slices`.

```json
{
  "config_version": "1.0",
  "slices": ["data_quality"],
  "measurement_ids": null,
  "expected_bundle_id": null,
  "data_quality": {
    "min_call_count": 10,
    "db_linkage_warning_percent": 99
  },
  "operations": {
    "series_baseline_measurement_id": null,
    "measurement_order": null,
    "min_comparison_count": 10
  }
}
```

- `measurement_ids: null` — все сохранённые замеры. Для отбора задайте непустой список точных `measurement_id`; неизвестные идентификаторы отклоняются.
- `expected_bundle_id` — необязательный SHA-256 для закрепления конкретного комплекта; получайте его через `--validate-only`. Это хеш реестра **11 файлов для 1.2–1.4, 16 для 1.5, 21 для 1.6**, а не повторный хеш исходных ТЖ.
- `min_call_count` — порог предупреждения о размере выборки, не доказательство статистической достаточности или приемлемой производительности.
- `db_linkage_warning_percent` — порог предупреждения о доле привязанных событий/времени DB, не SLA и не процент полноты исходного журнала.
- Неизвестные ключи, повторные имена, недопустимые типы, NaN/Infinity и повторные JSON-ключи отклоняются.
- `--slices` заменяет выбор срезов из конфигурации. Остальные настройки сохраняются; эффективная конфигурация записывается в результат. При выборе `apdex_overall` автоматически добавляется обязательный `apdex_composition`, в том числе для CLI-переопределения.
- `operations.series_baseline_measurement_id: null` — первый замер **полной серии в комплекте**, если порядок установлен. Можно явно задать существующий идентификатор опорного замера.
- `operations.measurement_order: null` — порядок по сохранённым временам. Для неоднозначного порядка можно явно перечислить **все** замеры комплекта в нужной последовательности; порядок списка сохраняется.
- `operations.min_comparison_count` — порог предупреждения о малой выборке; сам расчёт при N=1 не запрещается.
- Отбор `measurement_ids` ограничивает строки результата, **не меняя базовый замер, первое наблюдение или поиск предыдущего замера/наблюдения**. Сравнение может ссылаться на замер вне отобранных строк истории; его значения включены непосредственно в таблицу сравнений.

## Запуск в PowerShell

Команды выполняются из корня проекта. Если `python` отсутствует в PATH, укажите путь к своему интерпретатору.

```powershell
$TjSlicesTool = ".\tools\one_c_tj_analyzer\derive_slices.py"
$TjSavedBundle = ".\data\analysis\run_001"
$TjSlicesConfig = ".\tools\one_c_tj_analyzer\configs\slices.example.json"
$TjSlicesOutput = ".\output\slice_run_001"

& "python" `
  -B $TjSlicesTool `
  --analysis-dir $TjSavedBundle `
  --config $TjSlicesConfig `
  --output-dir $TjSlicesOutput `
  --slices data_quality
```

Проверка без записи файлов (включает расчёт выбранных срезов в памяти):

```powershell
& "python" `
  -B $TjSlicesTool --analysis-dir $TjSavedBundle --config $TjSlicesConfig --validate-only
```

Список доступных срезов: `python derive_slices.py --list-slices`. Версия: `python derive_slices.py --version`.

Входной и выходной каталоги не могут совпадать или быть вложены друг в друга. Конфигурация не может находиться в выходном каталоге. Новый или пустой выходной каталог разрешён. Непустой — только с явным `--overwrite` и только если это распознанный результат данного расчётчика без посторонних файлов, подкаталогов и символьных ссылок. Старый результат Анализатора ТЖ не считается допустимой целью перезаписи.

При перезаписи набор выбранных срезов должен совпадать с прежним: так в каталоге не останутся устаревшие таблицы от другого выбора. Для другой схемы или другого состава срезов используйте новый выходной каталог.

Запуск истории, сравнений, сопоставимости и качества:

```powershell
$TjOperationsConfig = ".\tools\one_c_tj_analyzer\configs\operations.example.json"
$TjOperationsOutput = ".\output\operations_run_001"

& "python" `
  -B $TjSlicesTool --analysis-dir $TjSavedBundle `
  --config $TjOperationsConfig --output-dir $TjOperationsOutput
```

Для одного среза добавьте, например, `--slices operation_history`. Выбор `measurement_comparisons` без `comparability` допустим: числовые строки всё равно содержат ключи, размеры выборок и статусы; полный набор ограничений удобно получать отдельной таблицей `comparability`.

Отдельный запуск DB-chatty (создаёт шесть таблиц DB-chatty, качество и манифест):

```powershell
$TjChattyConfig = ".\tools\one_c_tj_analyzer\configs\db_chatty.example.json"
$TjChattyOutput = ".\output\db_chatty_run_001"

& "python" `
  -B $TjSlicesTool --analysis-dir $TjSavedBundle `
  --config $TjChattyConfig --output-dir $TjChattyOutput
```

`--slices db_chatty` выбирает только таблицу групп, **не весь блок**. Для всех шести таблиц используйте предложенную конфигурацию без `--slices`. Для отдельных вызовов достаточно `--slices db_chatty_calls`, только для быстрых превышений — `--slices db_chatty_fast_calls`. Все таблицы рассчитываются независимо из CALL и не требуют ранее созданных выходов других срезов.

## Проверки входа

1. Схема, единицы измерения, обязательные поля/файлы, типы и корректность CSV/JSON.
2. Совпадение общих CSV/JSON-полей и числа строк с манифестом.
3. Уникальность CALL, источников, наборов, групп операций, строк привязки и ключей дополнительных таблиц.
4. `top_calls.csv` — точное уникальное подмножество CALL; JSON-состав каждой операции соответствует её CALL, а не только общему множеству идентификаторов.
5. Суммы CALL/CPU/DB/байтов/ошибок/блокировок, duration median/p95/p99/min/max и пороговые количества операций.
6. Соответствие интервала каждого CALL его длительности; неизвестные времена остаются неизвестными.
7. Суммы привязанных событий и времени DB, проценты, причины непривязки; сверка с event_stats наборов.
8. Согласованность записанных статусов файлов, исходного реестра хешей и `analysis_complete` — **без проверки оригиналов**.
9. Соответствие сохранённого SQL fingerprint сохранённому нормализованному SQL; повторная нормализация SQL не выполняется.

Это проверка сохранённых данных, а не доказательство безошибочного исходного парсинга. Полные SQL-события отсутствуют: SQL-перцентили, дедупликацию исходных событий и правильность конкретной DB → CALL-привязки заново проверить нельзя.

## Результат и воспроизводимость

- `data_quality.csv` — качество и ограничения по замерам.
- `operation_history.csv`, `operation_history_all_users.csv`, `measurement_comparisons.csv`, `comparability.csv` — создаются только при выборе соответствующих срезов.
- `db_chatty.csv`, `db_chatty_calls.csv`, `db_chatty_fast_calls.csv`, `db_chatty_duration.csv`, `db_chatty_coverage.csv`, `db_chatty_changes.csv` — независимые таблицы блока DB-chatty.
- `apdex.csv`, `apdex_calls.csv`, `apdex_uncovered.csv`, `apdex_coverage.csv`, `apdex_overall.csv`, `apdex_composition.csv`, `apdex_changes.csv` — таблицы APDEX; состав выборки обязателен для общего показателя.
- `problem_registry.csv`, `problem_history.csv` и пять отдельных выборок `problem_improved/persisting/worsened/new/unchecked.csv`; `problem_rule_coverage.csv` показывает доступность оценки правил, включая недоступность APDEX без T.
- `slice_manifest.json` — версии расчётчика/выходной и входной схем/анализатора, эффективная конфигурация, хеш исходного файла конфигурации и её нормализованного представления, SHA-256 и размеры всех входных файлов (16 для 1.5, 21 для 1.6), `bundle_id`, результаты проверок, список выбранных срезов, схема/число строк/хеш каждого выхода.

CSV: UTF-8 BOM, запятая, LF. Числа — без локализованных разделителей. `null` — пустая ячейка; объекты/списки внутри ячеек — JSON. Булевы значения — `true`/`false`.

Воспроизводимые файлы не содержат времени запуска или выбранного выходного пути. Путь результата печатается только в JSON в консоль. `data_quality` сохраняет порядок по минимальному времени начала CALL, затем идентификатору. В истории операции сортируются по точной сигнатуре, затем пользователю и порядку замеров полной серии; сравнения дополнительно по фиксированному порядку четырёх баз. Имена папок не используются как фактическое время. Перестановка наблюдений не меняет численные результаты, но изменение байтов входа меняет `bundle_id` и связанные с ним идентификаторы происхождения.

Хеши входных файлов сравниваются после загрузки и расчёта, перед публикацией. Изменение комплекта/конфигурации во время расчёта вызывает ошибку. Файлы результата сначала готовятся в отдельном временном каталоге; манифест публикуется последним. Прерывание между заменами файлов может оставить неполный результат — его выявляет проверка хешей. Рекомендуется новый каталог вместо перезаписи.

Код `0` означает согласованность комплекта и успешное выполнение, **не полноту источников и не принятую производительность**. `source_analysis_complete=false` переносится в выход и не превращает корректный расчёт частичных данных в ошибку. Неверный вход, конфигурация, выходной путь или нарушение согласованности дают код `2`, JSON с `status: ERROR` в stderr.

## Семантика data_quality

- `call_count`, уникальные сохранённые пользователи/сигнатуры/пары операция–пользователь — размеры наблюдаемой популяции, не количество бизнес-транзакций.
- `observed_call_start/end` — границы известных CALL, не чистое время теста. Отсутствующие времена не восстанавливаются по папкам.
- `calls_from_partial_sources` — точное число сохранённых CALL из источников с частичным статусом.
- `related_capture_*` — сведения обо **всей связанной выгрузке**. Пропущенный файл может не иметь достоверного дня/пользователя. Эти значения нельзя суммировать между днями одной выгрузки или приписывать конкретной операции.
- `source_completeness` всегда `not_established_from_saved_results`. Отдельно сохраняются исходный флаг `bundle_analysis_complete` и обнаруженные проблемы связанной выгрузки. Число потерянных CALL и процент полноты по размерам файлов не оцениваются.
- `db_linked_count_percent = 100 × Σlinked_count / Σtotal_count`; аналогично для времени. Проценты разных наборов не усредняются. При нулевом знаменателе значение отсутствует, а не равно 0 или 100.
- 100% привязки означает лишь привязку всех **разобранных** DB-событий. Это не доказательство полноты ТЖ или правильности временного сопоставления. Уверенность привязки отдельного CALL недоступна.
- `metric_availability` сохраняет количество имеющихся числовых значений и нулей. В схеме 1.2 отсутствие/невалидность CpuTime, InBytes, OutBytes, Memory, MemoryPeak и RowsAffected могла превратиться в 0. Поэтому `raw_missing_count` и `raw_invalid_count` остаются `null`; нули не объявляются фактическим отсутствием нагрузки.
- Ноль связанных DB-событий также не доказывает отсутствие обращений к БД: привязка и состав журналирования имеют ограничения.
- `unavailable_dimensions` и `known_limitations` явно сохраняют отсутствующие параметры, роли, документы, cold/warm, SessionID/OSThread на CALL, полный CALL → SQL, исход бизнес-операции и другие ограничения.

Замеры с метаданными, но без CALL, не исчезают: N=0, времена/доли без знаменателей пустые. Полностью пустой сохранённый комплект даёт таблицу с заголовком без строк и полноценный манифест.

## История операций: популяции, метрики и отсутствие наблюдений

Операция определяется **точным значением `signature`**. Сходные строки, разные имена методов, суффиксы, пользователи и Context не объединяются эвристически. Пользовательская история строится для пар сигнатура–пользователь, наблюдавшихся хотя бы однажды в полном комплекте, по всем выбранным замерам, включая периоды до первого наблюдения и после последнего.

Основные поля:

- `count` — N;
- `duration_us_sum`, `avg_us`, `median_us`, `p95_us`, `p99_us`, `max_us`;
- `duration_gt_1s_count`, `duration_gt_5s_count`, `duration_gt_10s_count`, `duration_gt_30s_count`;
- `db_count_sum`, `db_per_call`, `db_duration_us_sum`, `db_seconds_per_call`;
- `cpu_us_sum`, `cpu_us_per_call`, `cpu_us_max`, `cpu_percent_of_wall`;
- `in_bytes_sum/per_call/max`, `out_bytes_sum/per_call/max`;
- `memory_peak_avg/median/p95/p99/max`;
- `call_ids`, `history_id`, `operation_id`, `cohort_id` для воспроизведения состава;
- `counter_zero_counts` и `known_limitations` для ограничений счётчиков.

Все перцентили считаются из отдельных CALL. Median при чётном N — среднее двух центральных значений; p95/p99 — nearest-rank. Сводка всех пользователей пересчитывается из объединённой популяции CALL, а не из средних или перцентилей пользовательских групп. В схемах 1.3/1.4 CPU% — `100 × ΣCpuTime / ΣCALL duration` по одним и тем же CALL с доступным CpuTime; покрытие количества и времени публикуется отдельно. Это не среднее процентов отдельных вызовов. При суммарной длительности 0 CPU% отсутствует.

**Пороговые счётчики новых срезов используют строго `duration > порог`.** Это видно в именах `duration_gt_*`. Они намеренно не называются старыми `over_*`: в исходном анализаторе те означают `>=`. Числа ровно на границе проверяются тестом.

При отсутствии операции сохраняются `observation_status=not_observed`, `observation_label="не наблюдалась"`, `count=0`; все перечисленные показатели длительности/ресурсов/пороговых превышений пустые. Это не нулевая длительность и не исправление. Число CALL без времени или из частичного источника равно числу таких **сохранённых наблюдений**, не оценке потерянных событий.

`operation_history_all_users.csv` имеет `population_scope=all_users`, пустое поле `user` и список реально наблюдавшихся пользователей. `operation_history.csv` имеет `population_scope=same_user`. Эти представления перекрываются: **суммировать N или длительности между ними нельзя**.

## Четыре базы сравнения

Для каждой строки пользовательской истории формируются четыре строки с одинаковой точной сигнатурой и тем же ключом пользователя:

| comparison_basis | Значение |
|---|---|
| `series_baseline` | Один опорный замер всей серии; если этой пары там нет, reference_count=0 и нет дельт производительности |
| `first_observation` | Первое наблюдение данной пары сигнатура–пользователь в полной серии |
| `previous_observation` | Ближайшее предшествующее наблюдение этой пары, допускающее пропуск промежуточных замеров |
| `previous_measurement` | Непосредственно предыдущий замер полной серии, даже если пары там не было |

Если пользователь поменялся, его первое наблюдение не подменяется наблюдением другого пользователя. `first_operation_observation_all_users_measurement_id` в истории отдельно показывает начало наблюдения сигнатуры вообще; оно не является базой сравнения разных пользователей.

Пример: операция есть 04.08 и 19.08, но не наблюдается 11.08. Для 19.08 предыдущим наблюдением будет 04.08, а непосредственно предыдущим замером — 11.08 с N=0. Если вся серия начинается раньше первого появления операции, глобальная база остаётся прежней и не заменяется её первым наблюдением.

Для каждой метрики сохраняются суффиксы `_reference`, `_current`, `_delta_absolute`, `_delta_percent`. Абсолютное изменение — `current − reference`, процентное — `100 × изменение / reference`. При нулевой базе процент пустой, в том числе для 0 → 0. Такие метрики перечисляются в `percent_undefined_zero_reference_metrics`. Если отсутствуют наблюдения хотя бы с одной стороны, дельты производительности не рассчитываются.

`reference_count` и `current_count` — размеры обеих выборок; отдельные `sample_count_delta_*` описывают изменение N, **не производительности**. При известном замере без операции N=0; если предшествующего замера/наблюдения вообще нет, `reference_measurement_id` и `reference_count` пустые.

Единицы абсолютного изменения сохраняются: длительности — микросекунды (кроме `db_seconds_per_call`), объёмы и MemoryPeak — байты; `cpu_percent_of_wall_delta_absolute` — **процентные пункты**, а `_delta_percent` — относительное изменение CPU%. Уменьшение числа CALL, общего CPU или суммы времени при другом N само по себе не означает ускорения.

Сравнение первого замера с самим собой даёт нулевую абсолютную дельту; процент при нулевых показателях всё равно остаётся неопределённым. Если текущая строка находится раньше первого появления пары, база первого наблюдения может указывать вперёд: `reference_relation=later`, статус `before_first_observation`, без дельт производительности.

### Хронология и сопоставимость

По умолчанию порядок истории берётся из сохранённых времён CALL. Для замера без CALL используются сохранённые временные метаданные SQL/ошибок либо набора, относящегося к единственному замеру. Эти таблицы используются **только для порядка**, не как дополнительные CALL. Дни разных `measurement_id` не объединяются автоматически. Непосредственным предыдущим замером считается предыдущий идентификатор полной серии, а не предыдущая папка или предыдущая независимая бизнес-итерация.

При недостатке времён или равенстве стартов нескольких замеров сохраняется детерминированный технический порядок, но `series_order_reliable=false`; относительные базы не назначаются предположительно. Явный `operations.measurement_order` позволяет задать порядок. Явно выбранную глобальную базу можно использовать даже при неустановленном относительном порядке.

`comparability.csv` связывается с числовой таблицей **один к одному по `comparison_id`** и показывает:

- совпадение точной сигнатуры и пользователя **при наличии наблюдений с обеих сторон**;
- отдельно совпадение ключей (`key_*`), которое не доказывает наличие наблюдений;
- реально наблюдавшихся пользователей сигнатуры в обоих замерах; случай «раньше была только у другого пользователя»;
- различия N, наборов, идентификаторов процессов, качества источников и зарегистрированного покрытия DB;
- неизвестные роль, документ, параметры, объём данных, cold/warm, нагрузку, версии и настройки журналирования;
- предупреждение о N ниже настроенного порога.

Поля покрытия DB здесь относятся к **замеру целиком**, включая другие операции и пользователей; они не доказывают покрытие конкретной операции. Различие идентификаторов процессов — факт различия сохранённых идентификаторов, не установленная смена инфраструктуры. Совпадение сигнатуры/пользователя не превращает сравнение в контролируемый эксперимент. `interpretation` всегда указывает: числовое изменение **не является доказанным эффектом исправления кода**.

## DB-chatty: диагностический профиль, не норматив

Все численные наблюдения берутся из `call_observations.csv`: `db_count` — число **сохранённых связанных DBPOSTGRS**, `db_duration_us` — их сохранённая суммарная длительность. События SDBL к ним не добавляются. Количество DB-событий не трактуется как число уникальных SQL или сетевых round-trip.

Необязательный блок конфигурации и его значения по умолчанию:

```json
"db_chatty": {
  "thresholds": [100, 500, 1000, 5000],
  "duration_bounds_seconds": [1, 5, 10, 30],
  "fast_call_max_seconds": 1
}
```

Это **предлагаемые диагностические настройки**, не официальные нормы 1С, не SLA и не доказательство избыточности. Они нужны для отбора и сравнения профилей. Срез не ставит диагноз N+1 и не восстанавливает отсутствующую полную связь CALL → SQL.

`thresholds` — непустой список различных положительных целых чисел, нормализуемый сортировкой. `duration_bounds_seconds` — непустой список различных положительных границ; `fast_call_max_seconds` — неотрицательное число. Времена должны представляться целым числом микросекунд без потери точности при нормализации; субмикросекундные границы отклоняются. Настройки сохраняются в эффективной конфигурации манифеста и защищены контрольной суммой.

### Два разных показателя

Для группы «точная сигнатура + пользователь + замер» и каждого порога K:

1. `group_mean_above_threshold = (Σdb_count > K × N)` при N > 0. Это признак **среднего группы**. Поле `calls_in_mean_flagged_group_count` равно N, если признак установлен; это не число CALL с индивидуальным превышением.
2. `calls_above_threshold_count = count(CALL.db_count > K)`. Доля равна `100 × calls_above_threshold_count / call_share_denominator`, где знаменатель — **все сохранённые CALL данной группы**, в том числе с нулевым связанным DB.

Ровно K — не превышение. Предикат среднего проверяется целочисленно, без погрешности округлённого среднего. Проценты долей не округляются перед последующим сравнением.

Проверенные тестовые примеры при K=100:

- 50 CALL с нулём связанных DB и один с 5000: среднее 5000/51 ≈ 98,04, группа не проходит порог среднего, но один фактический CALL проходит.
- 9 CALL с нулём и один с 2000: среднее 200, группа проходит порог, но фактически превышает его только 1/10 CALL, а не 10/10.

При неотрицательных счётчиках среднее выше K **невозможно без хотя бы одного CALL выше K**. «Обратный случай» — большинство вызовов не превышает порог, хотя среднее группы превышает; не искусственный случай отсутствия всех индивидуальных превышений.

### Таблица групп — db_chatty.csv

Строка — одна пара операция–пользователь, замер и порог. Пары, наблюдавшиеся хотя бы однажды, сохраняются по всей выбранной серии, включая «не наблюдалась» с N=0. Не объединяйте строки разных порогов суммированием N: они описывают одну и ту же популяцию.

Поля:

- `count`, `calls_above_threshold_count`, `call_share_denominator`, `calls_above_threshold_percent`;
- `db_per_call_avg`, `db_per_call_median`, `db_per_call_p95`, `db_per_call_max`, `db_count_sum`;
- `call_duration_us_sum/avg/median/p95/max`;
- `linked_db_duration_us_sum`, `linked_db_seconds_per_call`;
- `chatty_call_duration_us_sum/avg/median/p95/max`, `chatty_db_count_sum`, `chatty_linked_db_duration_us_sum`, `chatty_linked_db_seconds_per_call` — **только фактически превысившие K CALL**;
- `fast_call_count`, `fast_calls_above_threshold_count`, `fast_call_share_denominator`, `fast_calls_above_threshold_percent`;
- `calls_with_zero_linked_db`, качество привязки замера и ограничения.

`fast_calls_above_threshold_percent` имеет знаменатель **все быстрые CALL группы**, не все её CALL и не все chatty CALL. Быстрый CALL определяется `duration_us <= fast_call_max_us`; по умолчанию ≤1 с. Это технический классификатор длительности, а не доказательство приемлемого бизнес-отклика.

Все распределения рассчитаны из индивидуальных CALL: median — среднее центральных значений при чётном N, p95 — nearest-rank. Времена в `*_us_*` — микросекунды; в `*_seconds_per_call` — секунды. Средний связанный DB time для всей группы делится на N, для chatty-подмножества — на число CALL с превышением. Суммы CALL и DB time не являются неперекрывающимся wall time; DB time не вычитается как доказанная исключительная часть CALL.

N=0 означает отсутствие сохранённых наблюдений: средние/перцентили/время пустые, численность подмножеств 0, доли без знаменателя пустые. При N>0 и отсутствии превышений сумма по пустому chatty-подмножеству равна 0, а его среднее/median/p95/max пустые. Нулевая доля наблюдаемых превышений не равна доказанному отсутствию обращений к БД.

### Отдельные CALL — db_chatty_calls.csv

Одна строка на сохранённый CALL, превысивший **хотя бы один** выбранный порог. CALL не дублируется, если превысил несколько порогов: они перечислены в `thresholds_exceeded`. Для конкретного порога проверяйте его присутствие в этом списке, а не только число строк таблицы. CALL без превышений отсутствуют в этой таблице, но учтены в знаменателях групп и охвата.

Сохранены `call_id`, `observation_id`, ключи операции/пользователя/замера, длительность CALL, связанное DB time и число событий, `is_fast_call`, диапазон длительности, исходный идентификатор источника и зарегистрированный статус его чтения. `group_mean_thresholds_exceeded` показывает отдельный признак среднего соответствующей группы и может отличаться от индивидуальных порогов. Записанный путь `source` — только происхождение; он не открывается.

**`db_chatty_fast_calls.csv`** — самостоятельная выбираемая таблица с теми же колонками: точное подмножество `db_chatty_calls.csv`, где `is_fast_call=true`. Для конкретного порога проверяйте `thresholds_exceeded`. Представления перекрываются: не добавляйте быстрые CALL к общему числу превышений и не суммируйте строки двух файлов как независимые наблюдения. При отсутствии быстрых превышений создаётся таблица с заголовком без строк.

### Распределение длительности — db_chatty_duration.csv

По умолчанию диапазоны: `[0;1]`, `(1;5]`, `(5;10]`, `(10;30]`, `(30;+∞)` секунд. Они непересекающиеся; граничный CALL относится ровно к одному диапазону. Пустая нижняя/верхняя граница означает отсутствие ограничения с этой стороны; исходные длительности валидируются как неотрицательные.

Для каждой **наблюдавшейся** группы и порога выдаются все диапазоны, включая пустые. Отсутствующая операция не получает выдуманного распределения; её статус остаётся в `db_chatty.csv`.

Два знаменателя различаются намеренно:

- `within_band_above_threshold_percent`: CALL с превышением в диапазоне / **все CALL диапазона** (`within_band_call_denominator`);
- `share_of_group_chatty_calls_percent`: CALL с превышением в диапазоне / **все CALL группы с превышением того же порога** (`group_chatty_call_denominator`).

При нулевом знаменателе доля пустая. Число CALL и время по диапазонам согласуются с группой; суммы можно складывать по диапазонам **только для фиксированных группы и порога**.

### Охват — db_chatty_coverage.csv

Два уровня: `measurement_all_users` по замеру и `selected_measurements_all_users` по всем отобранным замерам. Итог полной выбранной серии **пересчитывает множества** уникальных сигнатур/пользователей из CALL, а не суммирует их между замерами. Строки этих двух уровней перекрываются и не суммируются.

Три самостоятельные единицы:

| Единица | Числитель | Знаменатель |
|---|---|---|
| CALL | `chatty_call_count` | `call_share_denominator` = все CALL выбранного уровня |
| Операции | `affected_operation_count` = точные сигнатуры хотя бы с одним превышением | `operation_share_denominator` = все наблюдавшиеся сигнатуры |
| Известные пользователи | `affected_known_user_count` = идентификаторы хотя бы с одним превышением | `known_user_share_denominator` = все наблюдавшиеся известные идентификаторы |

Одинаковая сигнатура у разных пользователей считается одной уникальной операцией. Пустой пользователь, `(not specified)` и `(unknown)` не считаются установленными пользователями: их CALL выделены в `calls_with_unknown_user_count` / `chatty_calls_with_unknown_user_count`, но остаются в общей популяции CALL и операций. Идентификатор пользователя не доказывает число физических лиц.

Отдельно показаны число групп со средним выше порога, их уникальные операции/известные пользователи и число **всех CALL, принадлежащих таким группам** (`calls_in_mean_flagged_groups_count`). Оно не подменяет `chatty_call_count`. Группа для среднего остаётся «операция–пользователь–замер» даже в итоговой строке серии: нет скрытого усреднения разных замеров.

Доли для 100/500/1000/5000 описывают вложенные подмножества, а не взаимоисключающие категории: их нельзя суммировать. Для пустого комплекта таблица охвата содержит нулевую выбранную популяцию по каждому порогу, без выдуманных операций/пользователей; доли пустые.

### Динамика — db_chatty_changes.csv

Две независимые базы: `first_observation` и `previous_observation` точной пары «сигнатура–пользователь», из **всего сохранённого комплекта**, не только отобранных дат и не только CALL, проходящих порог. Первое наблюдение без превышений остаётся базой. Пропущенные промежуточные замеры допускаются при поиске предыдущего наблюдения; другой пользователь не подставляется вместо отсутствующего.

Сохраняются ID обеих сторон, N обеих выборок, порог, признаки среднего группы, значения метрик `_reference` / `_current`, изменения `_delta_absolute` / `_delta_percent`. Изменение доли в `_delta_absolute` измеряется в **процентных пунктах**; `_delta_percent` — относительное изменение самой доли. Изменения численности подмножеств и сумм времени при другом N сами по себе не доказывают улучшение скорости.

При нулевой базе процент изменения пустой, включая 0 → 0. Без наблюдений хотя бы с одной стороны дельты профиля не рассчитываются. При неоднозначной хронологии относительные базы не угадываются. `operations.measurement_order` позволяет явно задать порядок, как для истории операций.

`operation_comparison_id` связывает строку с существующим сравнением операции, а `comparison_id` дополнительно учитывает порог. Известные различия N, источников/процессов и зарегистрированного покрытия DB отражены рядом с неизвестными параметрами. Численное изменение помечено как `numerical_change_only_not_proven_code_effect`, а не подтверждённый эффект исправления.

### Ограничения привязки DB → CALL

Качество привязки наследуется из сохранённых результатов. Проценты покрытия относятся к **замеру целиком**, не к конкретному CALL, операции или пользователю. Они не позволяют скорректировать индивидуальный DB/CALL делением на общий процент покрытия. Такой пересчёт не выполняется.

Ноль связанных DB-событий может означать отсутствие записанных/привязанных событий, а не отсутствие работы с БД. Неполнота источников, неизвестная точность индивидуальной привязки и неоднозначность старых нулевых счётчиков сохраняются. Даже 100% зарегистрированного покрытия не доказывает полноту ТЖ или корректность каждого сопоставления.

## Повторная проверка результата

```powershell
& "python" `
  -B ".\tools\one_c_tj_analyzer\verify_slices.py" `
  --analysis-dir $TjSavedBundle --slices-dir $TjSlicesOutput
```

Верификатор проверяет происхождение, версии, конфигурацию, состав популяции и побайтово сопоставляет выход с повторным детерминированным расчётом. Он не читает оригинальные ТЖ, архивы или исходный файл конфигурации: используется сохранённая эффективная конфигурация. Хеш исходного файла конфигурации остаётся записью происхождения, а не заново проверенным внешним файлом.

## Автоматические тесты

```powershell
& "python" `
  -B -m unittest discover `
  -s ".\tools\one_c_tj_analyzer\tests" `
  -p "test_derive_slices.py" -v
```

Тесты строят маленькие синтетические **сохранённые комплекты**, не вызывают парсер и не читают ТЖ. Проверяются загрузка, ошибки схемы/CSV/JSON, идентификаторы и ссылки, счётчики, нулевые знаменатели, частичность, запрет доступа к записанным исходным путям даже для stat/exists, выбор срезов, перезапись, повреждение результатов, детерминизм и неизменность входа. Для тестов истории и сравнений используйте `-p "test_*slice*.py"`: они также покрывают пропущенный промежуточный замер, разных пользователей, N=1, нулевую базу, объединение наборов одного пользователя, прямой расчёт pooled-перцентилей, границы порогов, неизменность глобальной базы при отборе дат и неоднозначную хронологию. Реальный тест символьной ссылки пропускается, если ОС не разрешает её создание.

Тесты DB-chatty: `-p "test_slice_db_chatty.py"`; они также входят в `test_*slice*.py`. Проверяют среднее ниже порога при одном экстремальном CALL и высокое среднее при большинстве CALL ниже порога, строгие границы DB и длительности, отдельные знаменатели, уникальные операции/пользователей, неизвестного пользователя, быстрые CALL, конфигурацию, пропуски замеров, нулевую базу, пустые/частичные данные, запрет обращения к исходным путям и сети, воспроизводимость и отсутствие перезаписи без разрешения.
