# APDEX по зарегистрированным серверным CALL

Расчётчик срезов 1.8.0, выходная схема 1.8; вход — сохранённые схемы Анализатора ТЖ 1.2–1.6. Исходные ТЖ, архивы, генераторы отчётов, сеть и LLM не используются. Единственная популяция — `call_observations.csv`; прежние APDEX и предложенные T не импортируются из PDF, CSV-выводов, текста или старых обсуждений.

Это **APDEX по зарегистрированным серверным CALL, не end-to-end оценка пользовательского отклика**. Один CALL не равен бизнес-транзакции. Вложенные события, фоновые вызовы, фильтры журналирования и состав сценариев могут влиять на популяцию. Доля покрытых T CALL не является оценкой полноты исходного ТЖ.

## Запуск

Команды выполняются из корня проекта.

```powershell
$TjPython = "python"
$TjToolDir = ".\tools\one_c_tj_analyzer"
$TjSavedBundle = ".\data\analysis\run_001"
$TjApdexConfig = "$TjToolDir\configs\apdex.example.json"
$TjApdexOutput = ".\output\apdex_run_001"

& $TjPython -B "$TjToolDir\derive_slices.py" `
  --analysis-dir $TjSavedBundle --config $TjApdexConfig --output-dir $TjApdexOutput

& $TjPython -B "$TjToolDir\verify_slices.py" `
  --analysis-dir $TjSavedBundle --slices-dir $TjApdexOutput
```

Пример конфигурации **намеренно содержит пустые `targets` и `classes`**. Такой запуск выдаёт перечень непокрытых операций и нулевое покрытие T, но не придумывает APDEX. Возьмите точные `signature` из `apdex_uncovered.csv`, создайте собственную конфигурацию и задайте обоснованные цели. Новый расчёт сохраняйте в новый выходной каталог. Перезапись защищена существующим механизмом `--overwrite`, версии и выбранный состав должны соответствовать.

Для выбора таблиц можно использовать `--slices apdex apdex_coverage`. При `--slices apdex_overall` **автоматически добавляется `apdex_composition`**: общий показатель без состава выборки не экспортируется. Эффективный набор сохраняется в манифесте. Проверка без записи: `--validate-only`.

## Цели T и их происхождение

T не имеет значения по умолчанию. Если операция не сопоставлена ни с явной целью, ни с явным классом, APDEX не вычисляется. Нулевой/отрицательный T, NaN/Infinity, пустой источник, неизвестный статус, дубликаты и неоднозначное членство в классах отклоняются. T должен точно представляться целым числом микросекунд; дробные секунды допустимы.

Структурный пример ниже **не задаёт действующих целей для реальной системы**. Указанные 1 и 2 секунды — только иллюстрации формата, а имена сигнатур нужно заменить точными строками из комплекта:

```json
"apdex": {
  "targets": [
    {
      "signature": "ТОЧНАЯ_СИГНАТУРА_ОПЕРАЦИИ_А",
      "t_seconds": 1,
      "status": "engineering_proposal",
      "source": "Пример инженерного предложения; заменить своим обоснованием"
    }
  ],
  "classes": [
    {
      "class_id": "explicit_example_class",
      "signatures": ["ТОЧНАЯ_СИГНАТУРА_ОПЕРАЦИИ_А", "ТОЧНАЯ_СИГНАТУРА_ОПЕРАЦИИ_Б"],
      "t_seconds": 2,
      "status": "engineering_proposal",
      "source": "Пример явного класса; не согласованный SLA"
    }
  ],
  "min_call_count": 10,
  "failure_policy": "latency_only",
  "confirmed_failures": {"bundle_id": null, "calls": []}
}
```

Правила разрешения:

1. Только точное совпадение `signature`, без regex, wildcard, префиксов и эвристического объединения.
2. Цель конкретной операции имеет явный приоритет над целью класса. В результате сохраняется `overridden_class_id`.
3. Класс задаётся **явным непустым списком сигнатур**. Одна сигнатура не может состоять в нескольких классах, даже если T одинаков.
4. Все настроенные сигнатуры должны встречаться где-либо в полном входном комплекте; опечатки/неиспользованные правила дают ошибку, а не молча игнорируются. Фильтр `measurement_ids` не ограничивает эту проверку.
5. Одна эффективная конфигурация T применяется ко всей серии. Это сопоставление при одинаковой текущей цели, **не восстановление исторически действовавших SLA**.

Статусы целей:

- `engineering_proposal` — инженерное предложение, не обязательство бизнеса;
- `business_approved` — цель, объявленная утверждённой в конфигурации. В `source` укажите реальный документ/решение, ответственного и дату, если они известны.

Расчётчик сохраняет статус и источник, но **не проверяет действительность внешнего утверждения**. Сам по себе `business_approved` не доказывает наличие договорного SLA. Старые предложения автоматически не становятся бизнес-утверждёнными. Чтобы сравнить два альтернативных T для одной операции, используйте отдельные конфигурации и выходные каталоги, а не дублирующие правила.

В строках результатов: `t_seconds`, `t_us`, `four_t_us`, `target_id`, `target_kind`, `target_class_id`, `overridden_class_id`, `target_status`, `target_source`.

## Формула и границы

Для CALL с длительностью d и заданным T:

| Категория | Условие по длительности |
|---|---|
| `satisfied`, удовлетворительное | d ≤ T |
| `tolerating`, допустимое | T < d ≤ 4T |
| `frustrated`, неудовлетворительное | d > 4T |

Ровно T относится к удовлетворительным; ровно 4T — к допустимым. Проверка целочисленная в микросекундах. Нулевой по длительности CALL при T>0 удовлетворяет временному критерию, но это не доказательство успешного бизнес-результата.

`APDEX = (S + 0.5 × A) / N = (2S + A) / (2N)`.

В таблицах: `satisfied_count`, `tolerating_count`, `frustrated_count`, `apdex_denominator`, `apdex_numerator_twice`, `apdex`. При наличии T и N>0 сумма трёх категорий строго равна N. При N=0 APDEX пустой, а не 0 или 1.

При отсутствии T сохраняется наблюдаемое N (`count`), но `covered_call_count=0`, `apdex_denominator=0`, категории и APDEX пустые. Это означает **«не рассчитывалось»**, не «все неудовлетворительны». Отсутствующая операция остаётся «не наблюдалась» с N=0 и пустым APDEX.

## Политика неуспехов

Политика всегда записана явно в эффективной конфигурации и результатах:

- `latency_only` — категория только по длительности. Это режим по умолчанию, **не предположение об успешности всех CALL**.
- `confirmed_failures_frustrated` — перечисленные подтверждённые неуспехи относятся к `frustrated` независимо от длительности и **остаются в N**. Если CALL уже был d>4T, он не учитывается дважды.

`EXCP`, QERR, `error_count` и факт привязки ошибки не являются подтверждением неуспешной бизнес-операции. `calls_with_linked_error_events` — число CALL с ненулевым сохранённым счётчиком связанных ошибок, не число независимых инцидентов. Наличие и отсутствие таких ошибок не доказывают исход выполнения.

Пример структуры подтверждения (не готовые данные для реального запуска):

```json
"failure_policy": "confirmed_failures_frustrated",
"confirmed_failures": {
  "bundle_id": "<фактический SHA-256 идентификатор комплекта из --validate-only>",
  "calls": [
    {"call_id": 123, "evidence": "<подтверждение связи этого CALL с неуспешным выполнением>"}
  ]
}
```

Требуются совпадение `bundle_id`, существующий уникальный положительный `call_id` и непустое описание/ссылка на подтверждение. Документы по ссылкам не открываются: это явная внешняя аннотация оператора расчёта, а не независимая проверка факта программой. Без совпадения комплекта ID из другой выгрузки не принимаются. Непустой список подтверждений при `latency_only` отклоняется как противоречивая настройка.

Если T отсутствует, даже подтверждённый неуспех остаётся вне APDEX; он отражается в `uncovered_confirmed_failure_count`. Пустой список подтверждений не доказывает отсутствие неуспехов.

Поля аудита:

- `confirmed_failure_count` — число явно аннотированных CALL;
- `business_outcome_unknown_count` — остальные CALL; они не считаются доказанно успешными;
- `latency_frustrated_count` — число d>4T до применения политики;
- `forced_frustrated_count` — число подтверждённых неуспехов, переклассифицированных из S/A в F;
- в `apdex_calls.csv` — `latency_category`, итоговая `category`, `confirmed_failure`, `failure_evidence`, `business_outcome` и сохранённый `linked_error_count`.

## Выходные таблицы

| Таблица | Содержание |
|---|---|
| `apdex.csv` | Полная сетка наблюдавшихся пар операция–пользователь по выбранным замерам: T, источник, статус, N, S/A/F, APDEX, покрытие и ограничения |
| `apdex_calls.csv` | Отдельные CALL **только с заданным T**, их категории и основания; не дополнительная популяция к группам |
| `apdex_uncovered.csv` | Наблюдавшиеся группы без T, с N; точные сигнатуры для заполнения конфигурации |
| `apdex_coverage.csv` | Покрытие T по CALL и уникальным операциям, по замеру и всей выбранной серии |
| `apdex_overall.csv` | Общий APDEX раздельно для `business_approved` и `engineering_proposal`, по замерам и выбранной серии |
| `apdex_composition.csv` | Обязательный состав каждого общего показателя: операция, пользователь, замер, T, N, вес, S/A/F и вклад |
| `apdex_changes.csv` | Динамика одинаковых операций и пользователей с явно указанными базами и ограничениями |

Покрытие: `covered_call_count / call_share_denominator` и `covered_operation_count / operation_share_denominator`. Знаменатели — все наблюдавшиеся CALL и уникальные точные сигнатуры соответствующего уровня. Операция у нескольких пользователей или в нескольких замерах учитывается одной уникальной сигнатурой в итоговом охвате. По статусам T показаны отдельные числители. Непокрытые CALL не исчезают из описания выборки, но **не включаются в знаменатель APDEX**.

Строки уровней «замер» и «выбранная серия» перекрываются; их нельзя суммировать. `user_identifier_count` общего показателя — количество сохранённых меток пользователя, включая неизвестные, а не число установленных физических лиц. Для точного состава смотрите `apdex_composition.csv`.

`min_call_count` по умолчанию 10 — настраиваемый порог предупреждения, не доказательство статистической достаточности. При N=1 APDEX вычисляется, но `small_sample_warning=true`; при N=0 показатель отсутствует. Информация о частичных источниках и неизвестных параметрах не устраняется достаточным N.

## Общий APDEX и изменение состава

Общий показатель считается из **суммарных количеств категорий CALL**, а не средним APDEX групп. Цели разных статусов не смешиваются. При разных T операций используется T каждой операции, а распределение этих целей видно в составе; общего скалярного T не выдумывается.

Каждая строка `apdex_overall.csv` содержит `overall_id`, `composition_file`, `composition_row_count`, N, численность без T и с другим статусом T. В составе по этому `overall_id` даны `call_weight_percent`, `operation_user_measurement_apdex`, `apdex_numerator_twice` и `contribution_to_overall_apdex`. Сумма вкладов равна общему APDEX с обычной точностью float; точная проверка возможна через целый числитель `2S+A`.

Контрольный пример из тестов:

- операция А всегда удовлетворительная (APDEX=1), Б всегда неудовлетворительная (APDEX=0);
- первый замер: 1 вызов А и 9 Б → общий APDEX=0,1;
- второй замер: 9 вызовов А и 1 Б → общий APDEX=0,9;
- APDEX обеих отдельных операций **не изменился**. Общий рост вызван только составом выборки.

Поэтому общий APDEX не объявляется улучшением кода или итогом исполнения SLA. В этом слое нет искусственной стандартизации весов и причинного заключения по общему показателю. При отсутствии покрытых CALL строки общего показателя имеют N=0 и пустой APDEX; состав пустой, но файл с заголовком существует.

## Динамика и сопоставимость

Используются четыре базы существующего слоя операций: базовый замер всей серии, первое наблюдение данной пары, предыдущее наблюдение пары и непосредственно предыдущий замер. Фильтр дат ограничивает выход, но не меняет поиск баз во всём комплекте. Пропуски не превращаются в нулевой APDEX.

Сопоставление — точная сигнатура + одинаковый известный идентификатор пользователя + та же эффективная цель/политика. Неизвестные метки пользователя не доказывают совпадение лиц: `user_identity_unknown`, без APDEX-дельт. Роли, документы, объёмы, параметры, cold/warm, нагрузка и бизнес-результаты могут оставаться неизвестными; это не контролируемый эксперимент. Если временной порядок не установлен, относительные базы не угадываются.

Сохраняются обе базы T, ID и размеры выборок, источники/статусы целей, категории и изменения. `apdex_delta_absolute = current − reference` — изменение на шкале APDEX 0…1; умножение на 100 даёт процентные пункты, если APDEX отображается в процентах. `apdex_delta_percent` — относительное изменение; при нулевой базе пусто, даже для 0→0. Различие количества подтверждений неуспехов отмечено отдельно: изменение политики/полноты внешней аннотации также требует осторожности.

Все численные изменения маркируются `numerical_change_only_not_proven_code_effect`. Стабильная конфигурация обеспечивает повторяемый расчёт при текущих целях, но не подтверждает, что эти цели были согласованы во время прошлых замеров.

## Проверки

```powershell
& $TjPython -B -m unittest discover -s "$TjToolDir\tests" -p "test_slice_apdex.py" -v
```

Тесты используют синтетические сохранённые комплекты. Проверяются формула, T±1 мкс и 4T±1 мкс, отсутствие T, N=0/N=1, разные статусы целей, классы/приоритеты/опечатки, неуспехи с привязкой к комплекту и CALL, отсутствие автоматического вывода из EXCP, покрытие, смена состава, нулевая база, пропуски/пользователи, обязательность состава общего APDEX, отсутствие обращений к исходным путям/сети, воспроизводимость и неизменность входа.

Общие правила версии схемы, хеширования, экспорта и защиты от перезаписи: [SLICES_RUNBOOK.md](SLICES_RUNBOOK.md). В манифесте сохраняются эффективные T, их статусы/источники, политика неуспехов, контрольные суммы конфигурации и входных файлов. Числовой результат не зависит от выходного пути или времени запуска.
